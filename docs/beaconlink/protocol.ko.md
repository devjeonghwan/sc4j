# Beacon.Link 프로토콜 참조, 프로토콜 1

[English](protocol.md) | **한국어**

Beacon.Link는 모든 SC4J가 실행하는 피어(런처의 노드, 런타임의 내장 피어, [운영 가이드](operator.ko.md)의 헤드리스 노드)로 이루어진 네트워크를 통해 SC4J 플레이어가 서로를 찾고, 플레이어 사이의 암호화된 채널로 플레이하게 합니다. 중앙 서버는 없습니다. 이 문서는 현재의 와이어 형식을 그대로 설명합니다. 피어와 클라이언트의 메시지(모듈 `sc4j-beaconlink-protocol`), 피어와 클라이언트의 수신 규칙(모듈 `sc4j-beaconlink-peer`, `MeshPeer`), 참가자 사이의 채널 신호와 데이터그램(모듈 `sc4j-beaconlink`), 파일입니다. 세부 규범은 이름이 나온 클래스의 Javadoc입니다.

따로 적지 않으면 모든 정수는 빅엔디언이고 부호가 없습니다. 데이터그램은 최대 1200바이트입니다. 텍스트는 1바이트 길이가 앞에 붙은 UTF-8이며, 잘못된 UTF-8은 거부합니다. 주소는 주소 체계(1바이트, `4` 또는 `6`), 4 또는 16바이트의 주소, 포트(2바이트)이며, 읽는 동안 이름을 조회하지 않습니다. 모든 읽기는 잘린 필드, 범위를 벗어난 값, 남는 바이트를 예외 없이 거부합니다.

## 정체성

모든 계정에는 플레이어 키(`accounts/<id>/identity.key`)가, 모든 피어에는 피어 키(런처 노드의 `peer.key`, 헤드리스 노드의 `<state>/identity.key`, 런타임 실행의 내장 피어는 그 실행을 위해 메모리에 만든 키)가 있습니다. 모두 Ed25519 키 쌍(JDK 내장)이며, 32바이트 공개 키가 정체성입니다. 플레이어 키는 방, 접속 상태, 채팅 줄, 귓속말, 신호에 서명하고 플레이어의 정체성(`LinkPlayer`)이 됩니다. 화면에는 `Name#abcd12`(계정 이름과 키의 SHA-256 앞 16진수 6자리, `IdentityKey.getTag`)로 보입니다. 피어 키는 라우팅 정체성일 뿐이며 화면에 보이지 않습니다. 키는 런처가 만들거나(새 계정의 플레이어 키) 처음 쓸 때 만들어집니다(피어 키). 사용자가 키를 입력하거나 붙여 넣는 일은 없습니다. 키 파일(`IdentityKeyFileUtils`): 매직 `BLKF`, 버전 `1`, 개인 키 바이트, 공개 키 바이트. 폴더 안의 임시 파일을 거쳐 원자적으로 쓰며, POSIX 파일 시스템에서 JDK는 이 임시 파일을 소유자만 읽을 수 있게 만들고(`rw-------`), 바뀐 파일은 이 모드를 유지합니다. 새 키는 새 정체성입니다.

**연결**: 계정 하나를 여러 장치(런처, 게임, 다른 컴퓨터)에서 동시에 쓸 수 있습니다. 클라이언트 세션 하나가 그 계정의 연결 하나입니다. 세션은 시작할 때 무작위 연결 번호(8바이트)를 뽑아 끝날 때까지 유지하며, 그 시작 시각의 에포크 밀리초가 연결 시작 시각입니다. 참가자(`LinkParticipant`)는 플레이어 키와 연결 번호의 쌍이며, 와이어 형식으로는 키(32)와 번호(8)입니다. 등록, 방, 신호, 채널, 오버레이, 로비, 락스텝 전송은 참가자 하나를 가리키므로, 계정 하나의 두 연결이 나란히 등록하고 방을 열고 채널을 가질 수 있으며, 서로 사이에도 그렇습니다. 친구, 접속 상태, 채팅 줄, 귓속말, 무시 목록은 플레이어(`LinkPlayer`) 단위입니다. 연결 번호는 비밀이 아닙니다. 어느 연결이든 등록하려면 플레이어 키와 그 스탬프가 필요합니다.

**플레이어 이름**(`PlayerNameUtils`. 런처, 계정 저장소, 모든 피어가 쓰는 단일 정의): 입력한 이름을 Unicode NFC로 바꾸고, 앞뒤 공백을 없애고, 안쪽의 연속 공백을 공백 하나로 바꾼 것입니다. 1에서 32 UTF-8 바이트이며, `#`와 제어, 서식, 사용자 정의 영역, 서로게이트, 미할당 문자는 쓸 수 없습니다. 올바른 이름은 정규화한 결과가 자기 자신입니다. 이름은 계정을 만들 때 정해집니다. 플레이어 스탬프가 이름을 키에 묶으므로(아래) 다른 이름은 다른 계정입니다.

**계정**(`AccountStore`, `Account`): 런처는 설치본의 플레이어 계정을 보관하며, 계정마다 id(키의 SHA-256 앞 16진수 16자리. 태그가 그 앞부분)로 이름 붙인 폴더 하나에 키, 이름과 그 플레이어 스탬프, 친구, 무시(차단)한 플레이어를 둡니다. 계정은 저절로 만들어지지 않습니다. 사용자가 만들거나(이름, 무작위 키, 둘의 스탬프) 가져오고, 게임을 실행할 계정을 고릅니다. 런처는 그 폴더를 런타임에 넘깁니다(`--account <dir>`). 이름 변경은 없습니다. 계정을 쓰는 모든 프로세스(게임, 런처의 세션)는 잠금 파일의 공유 잠금을 잡습니다(`AccountLock`). 몇 개든 계정 하나를 동시에 쓸 수 있고, 쓰는 동안에는 계정을 지울 수 없습니다(삭제는 배타 잠금을 잡습니다). 계정 없는 실행은 `Guest`라는 이름의 게스트로 플레이하며, 그 키와 스탬프는 실행 동안 메모리에만 있습니다. 백업 파일(`AccountBackup`, `.sc4jaccount`)은 계정을 그 이름 그대로 다른 설치본으로 옮깁니다. 매직 `BLKA`, 버전 `1`, 플래그(비트 0: 비밀번호로 보호), 보호된 백업이면 솔트(16), PBKDF2-HMAC-SHA256 반복 횟수(4), AES-GCM nonce(12), 그다음 본문(이름, 스탬프 난이도(1), 스탬프 nonce(8), 키 파일, 친구, 무시한 플레이어)입니다. 보호된 경우 본문은 비밀번호에서 얻은 키로 AES-256-GCM 암호화하며, 헤더를 연관 데이터로 씁니다. 스탬프가 이름을 키에 묶지 않는 백업과 그 밖의 파일(키 파일 단독 포함)은 거부합니다.

**게임 명령줄**: 런타임 실행은 Beacon.Link 설정을 설치 폴더 구조가 아니라 명령줄에서만 가져옵니다. `--account <dir>`(계정 폴더. 없으면 게스트), `--seeds <file>`(노드 목록), `--seed <host:port>`(반복 가능), `--peers <file>`(공유 피어 파일. 없으면 학습한 피어를 읽지도 보관하지도 않음). `--seeds`, `--seed`, `--peers` 중 하나가 있을 때만 Beacon.Link를 제공합니다. 런처는 계정 폴더, 단일 시드 규칙에 따른 시드(사용자가 저장한 `nodes.json`, 없으면 함께 배포된 `seeds.json`), 설치본의 `peers.json`을 넘깁니다. 게임을 직접 시작하는 사람도 같은 것을 넘기거나 아무것도 넘기지 않습니다. 실행의 내장 피어는 그 실행을 위해 메모리에 만든 키를 쓰는 리프이므로, 두 실행이 피어 키를 공유하지 않고 남는 것도 없습니다. 런처의 노드는 컴퓨터의 오래 사는 피어입니다. 설치본에서 처음 연 런처가 `node.lock`을 잡고 `peer.key`로 노드를 실행하며, 다른 런처는 실행하지 않다가 첫 런처가 닫힌 뒤 노드를 넘겨받습니다.

**피어 ID**(`PeerId`): ASCII 텍스트 `BLNK peer id 1`, 피어 키, 그 증명 nonce(8)의 SHA-256입니다. `BLNK peer proof 1`, 키, nonce의 SHA-256이 0 비트 20개로 시작하면 증명 nonce가 유효합니다(네트워크의 난이도. 피어는 시작할 때마다 가장 작은 유효 nonce를 찾으며, 데스크톱 코어 하나로 약 0.1초). 그래서 누구도 ID의 위치를 고를 수 없고, 모든 ID에는 작업 비용이 듭니다. 받는 쪽은 피어의 ID를 쓰기 전에 증명을 확인합니다. ID는 XOR 거리로 비교합니다(Kademlia).

**플레이어 스탬프**(`PlayerStamp`): `BLNK player stamp 1`, 플레이어 키, 이름의 UTF-8 길이(1), 이름, nonce(8)의 SHA-256 해시가 0 비트 24개로 시작하고 이름이 올바른 플레이어 이름이 되게 하는 nonce입니다. 런처가 계정을 만들 때 한 번 찾아 `account.json`에 보관합니다. 모든 등록, 접속 상태, 채팅 줄은 이름과 nonce를 담습니다. 피어와 클라이언트는 보낸 쪽 키와 담긴 이름의 스탬프를 확인하므로, 스탬프가 묶지 않은 이름은 거부되고, 키는 새 스탬프의 작업(새 계정과 같은 양) 없이는 다른 이름을 보일 수 없습니다.

## 역할

- 전체 피어: 도달성 자체 시험으로 모르는 상대가 소켓에 닿는다는 것이 확인된 피어. 전체 피어만 라우팅 테이블, `PEERS` 응답, 토픽의 저장 피어 집합, `peers.json`에 들어가며, 토픽 알림을 저장하고 토픽 메시를 이룹니다.
- 리프: 자체 시험으로 확인되지 않은 피어(`NOT_VERIFIED` 또는 `NOT_REACHABLE`). 다른 피어처럼 조회하고 인사하고 답하며, 대화하는 피어에게는 테이블 밖에서 알려져 있습니다. 나중 시험에서 확인되면 스스로 승격합니다.
- 리프 전용 피어(`PeerConfiguration.isLeafOnly`): 무엇이 오든 전체 피어가 되지 않습니다. 카드는 항상 닿을 수 없다고 하고, 다이얼백을 요청하지 않습니다. 다른 피어의 자체 시험에서 도우미와 제3 피어 역할은 계속 합니다. 끔 역할의 런처 노드가 리프 전용입니다.
- 홈 피어: 클라이언트 연결이 등록(`REGISTER`)한 피어. 클라이언트에게 관찰된 주소를 알려 주고, 클라이언트 대신 그 토픽에 참여해 레코드를 보내 주고, 등록한 연결 사이의 신호와 그 연결로 가는 귓속말을 중계합니다. 클라이언트는 최대 3개의 홈 피어(처음 등록한 노드들)에 등록합니다. 런타임 세션은 시드와 학습한 노드의 클라이언트이며 같은 소켓에서 내장 리프 피어를 실행합니다. 런처의 노드와 헤드리스 노드는 자기 소켓에서 홀로 실행됩니다(`PeerSocket`, `PeerBootstrap.run`).
- 참가자: 방에 있는 플레이어의 연결 하나. 게임 트래픽은 참가자 사이의 채널로만 흐르며([채널](#참가자-사이의-채널-sc4j-beaconlink-channel-패키지) 절), 그 게임의 참가자가 아닌 피어는 이를 나르지 않습니다.

## 엔벨로프 (`Envelope`, `MessageEncoder`)

| 필드 | 바이트 | 의미 |
|---|---|---|
| magic | 4 | `BLNK` |
| version | 1 | `1` |
| kind | 1 | 메시지 종류 코드(아래) |
| flags | 1 | 비트 0: 응답(응답에는 답하지 않음). 나머지 비트는 0 |
| request number | 4 | 요청자가 고름. 응답은 같은 번호를 씀 |
| timestamp | 8 | 보낸 쪽 벽시계, 에포크 밀리초(부호 있는 64비트) |
| nonce | 8 | 메시지마다 무작위, 재전송마다도 새로 |
| sender key | 32 | 보낸 쪽의 Ed25519 공개 키 |
| body length | 2 | |
| body | n | 종류별 내용 |
| padding length | 2 | |
| padding | p | 0 바이트 |
| signature | 64 | 앞의 모든 바이트에 대한 보낸 쪽의 Ed25519 서명 |

헤더는 61바이트, 트레일러는 `2 + p + 64`입니다. 모든 필드가 서명 안에 있지만 엔벨로프는 받는 쪽을 밝히지 않습니다. 서명된 데이터그램은 어느 피어에서나 유효하므로, 받는 쪽은 복사본이 보낸 쪽을 대신해 동작하게 두지 않습니다(nonce 확인이 키 속도보다 먼저이고, 벌점은 주소가 증명되었을 때만 키 단독과 주소 단독을 그레이리스트에 올립니다. [수신](#수신) 절).

**요청 번호**: 피어 계층은 요청 번호를 무작위로 뽑으므로(아직 기다리는 번호는 제외), 요청 하나를 본 누구도 다음 번호를 예측할 수 없습니다. 예를 들어 시드 대신 시드의 hello에 답하는 일을 막습니다. 토픽 계층, 자체 시험, 클라이언트는 무작위 시작값부터 하나씩 셉니다. 요청자는 기다리는 요청 번호를 가지고, 요청한 주소에서 왔으며, 알고 있다면 예상한 키를 가진 응답만 받아들입니다.

**패딩**: 자신을 증명하지 않은 주소로 보내는 요청(`PING`, `REGISTER`, `HELLO`, `DIAL_BACK`)은 256바이트로, `FIND_PEERS`는 617바이트(가장 긴 `PEERS` 응답)로, `GET_TOPIC`은 1155바이트(가장 긴 `TOPIC_PEERS` 응답)로 패딩합니다. 피어는 증명되지 않은 주소에 요청보다 많은 바이트로 답하지 않습니다. 더 길어질 응답은 보내지 않습니다(`UNPADDED`로 셈). 거부도 마찬가지입니다(`PUBLISH_ROOM`, `LIST_ROOMS`, `SIGNAL`, `PUBLISH_RECORD`, `RECENT`에 대한 `NOT_REGISTERED`, `ANNOUNCE`, `GRAFT`에 대한 `INVALID`).

## 수신

### 피어에서 (`MeshPeer.receive`)

서명 작업 전에 값싼 확인부터 이 순서로 합니다. 실패한 것은 버리고, 세고, 절대 답하지 않습니다.

1. 길이(최대 1200바이트. `OVERSIZE`)
2. 출발지 IP 주소의 속도(순간 256, 그 뒤 초당 128. `ADDRESS_RATE`)
3. 주소 그레이리스트(`GRAYLISTED`)
4. 엔벨로프 구조와 그 종류의 본문(`MALFORMED`). 클라이언트만 받는 응답(`OBSERVED_ADDRESS`, `ROOM_LIST`. `UNEXPECTED_REPLY`). 피어 자신의 키(`OWN_KEY`)
5. 타임스탬프 창, 받는 쪽 시계 기준 앞뒤 30초(`OUTSIDE_WINDOW`)
6. 서명(`FORGED`)
7. 키 그레이리스트와 주소별 키 그레이리스트(`GRAYLISTED`)
8. nonce: (보낸 쪽 키, nonce) 쌍을 창의 두 배 동안 기억합니다. 전체 65536개, 출발지 IP 주소 하나당 최대 2048개이며, 캐시가 차면 잊지 않고 새 메시지를 거부합니다(`REPLAYED`, `REPLAY_SOURCE_FULL`, `REPLAY_CACHE_FULL`).
9. 보낸 쪽 키의 속도(순간 32, 그 뒤 초당 16. `KEY_RATE`). 새롭고 올바르게 서명된 메시지에만 매기므로, 위조되거나 재전송된 복사본이 다른 키의 속도를 쓰지 못합니다.

그다음 그 종류의 처리기가 실행됩니다. 처리기는 쓰지 않은 것을 셉니다. `UNPADDED`(위), `NOT_A_PEER`(그 주소에서 알려진 피어가 보내지 않은 피어 메시지, 또는 기다리는 요청이 없는 응답), `INVALID_PROOF`(증명 nonce가 유효하지 않은 카드), `INVALID_ENTRY`(`PEERS`나 `TOPIC_PEERS` 응답에서 쓰지 않은 항목, 항목마다), `UNREQUESTED_PROBE`, `NOT_IN_TOPIC`, `INVALID_RECORD`(레코드마다), `COORDINATE_OUTLIER`(표본마다, [네트워크 좌표](#네트워크-좌표-networkcoordinate-coordinatereport-coordinateestimator) 절). 예외를 던지는 처리기는 피어의 결함입니다. 데이터그램은 잃고, 예외는 로그에 남기고 `DEFECT`로 세며, 소유자의 루프에는 아무것도 전달되지 않습니다. 카운트는 피어가 멈출 때 로그에 남습니다(헤드리스 노드는 한 시간마다도).

### 벌점과 그레이리스트 (`Graylist`)

| 벌점 대상 | 점수 |
|---|---|
| 잘못된 레코드: 다른 토픽이나 그곳에 속하지 않는 종류, 잘못된 서명이나 스탬프, 너무 긴 수명 | 10 |
| 증명이 위조된 카드 | 10 |
| 작성자 속도를 넘은 레코드 | 2 |
| 만료된 레코드, 토픽 메시 밖의 피어가 보낸 토픽 메시지, 요청 없는 응답, 패딩 없는 요청, 안정된 좌표가 거부한 좌표 표본 | 1 |

점수는 키와 출발지 주소별로 세고, 마지막 벌점 뒤 60초가 지나면 잊습니다. 40점이 되면 그 주소의 그 키를 10분 동안 그레이리스트에 올립니다. 주소가 그 키에 대해 증명되었으면(토큰으로 graft한 메시 이웃, 그 주소에서 답한 라우팅 연락처, 등록한 클라이언트) 키 단독과 주소 단독(IP 주소 전체, 모든 포트. 루프백에서는 소켓 주소)도 함께 올립니다. 그러면 그곳에서 온 모든 데이터그램을 서명 확인 전(주소)이나 직후(키)에 버리고, 그 피어는 모든 메시, 멤버 목록, 저장된 알림에서 빠집니다. 증명되지 않은 출발지 주소는 위조될 수 있고 서명된 데이터그램은 다른 곳에서 재전송될 수 있으므로, 어느 쪽도 다른 호스트를 그레이리스트에 올리게 할 수 없습니다. 벌점과 그레이리스트는 로컬입니다. 공유하는 평판은 없습니다.

### 클라이언트에서 (`BeaconLinkClient`)

세션 소켓은 채널 데이터그램(매직 `BLCH`, [채널](#참가자-사이의-채널-sc4j-beaconlink-channel-패키지) 절)과 엔벨로프를 나릅니다. 내장 피어가 있으면, 엔벨로프는 다음 경우에만 세션에 남고 나머지는 피어로 갑니다. 기다리는 세션 요청에 대해 그 요청의 노드가 보낸 응답이나 세션 귓속말에 대한 응답, 세션의 노드가 보낸 세션 키 앞의 신호나 귓속말, 피어가 참여하지 않는 토픽에 대해 세션의 노드가 보낸 푸시입니다. 세션이 받는 것은:

- 응답: 기다리는 요청 번호를 가지고, 요청한 노드에서, 창 안에서, 올바르게 서명되고, 노드의 키(고정한 키, 또는 세션에서 그 노드의 첫 응답의 키. 다른 키면 그 노드를 잘못된 키로 답하는 노드로 표시)를 가지며, nonce가 새것인 경우
- 신호: 등록한 노드에서, 자기 키와 연결 앞으로, 자기 참가자(보낸 쪽 키와 페이로드가 밝힌 연결)가 보낸 것이 아니고, 창 안에서, 올바르게 서명된 경우. 가지고 있거나 기다리는 채널의 신호와 자기가 연 방의 참가 신호에만 반응하고, 재전송 방지를 위해 기억합니다(보낸 쪽 키마다).
- 푸시(`GOSSIP`, `IHAVE`, `SEALED`): 등록한 노드에서, 노드의 키(귓속말은 보낸 사람의 키)를 가지고, 창 안에서, 올바르게 서명된 경우. 푸시된 모든 레코드는 중계자처럼 확인하고, 귓속말의 nonce는 보낸 사람 아래 기억합니다.

실패한 데이터그램은 버리고 출발지별로 셉니다. 처리 중 결함은 로그에 남기고 폴링을 계속합니다.

## 메시지 종류 (`MessageKind`)

| 코드 | 종류 | 방향 | 본문 |
|---|---|---|---|
| 1 | `REGISTER` | 클라이언트 -> 홈 피어 | 토큰(길이 바이트, 최대 32바이트), 수명 초(2. `0`이면 그 연결의 등록 삭제), 표시 이름(텍스트, 최대 32바이트), 스탬프 nonce(8), 모드 지문, 연결 번호(8), 연결 시작(에포크 ms, 8), 플래그(1, 모두 0) |
| 2 | `OBSERVED_ADDRESS` | `REGISTER`에 대한 응답 | 상태(1, 아래), 관찰된 주소, 허용한 수명 초(2), 토큰(길이 바이트 + 바이트. `TOKEN_REQUIRED`와 함께), 피어의 좌표 보고(17) |

| 5 | `ROOM_LIST` | `LIST_ROOMS`에 대한 응답 | 토픽의 전체 방 수(2), 페이지 오프셋(2), 개수(1)와 광고들 |

| 16 | `PEERS` | `FIND_PEERS`에 대한 응답 | 답하는 피어의 좌표 보고(17), 개수(1, 최대 8)와 항목: 키(32), 증명 nonce(8), 주소. 답하는 피어의 라우팅 테이블에서 대상에 가장 가까운 전체 피어이며, 묻는 쪽은 뺍니다. |
| 17 | `GET_TOPIC` | 피어 -> 저장 피어나 멤버. 1155바이트로 패딩 | 토픽 키(33) |

| 19 | `ANNOUNCE` | 멤버 -> 저장 피어 | 토픽 키(33), 보낸 쪽 카드, 저장 피어가 보낸 쪽에게 준 토큰 |
| 20 | `GRAFT` | 멤버 -> 멤버 | 토픽 키(33), 보낸 쪽 카드, 상대 멤버가 보낸 쪽에게 준 토큰 |
| 21 | `PRUNE` | 멤버 -> 메시 이웃 | 토픽 키(33). 답하지 않음 |
| 22 | `GOSSIP` | 멤버 -> 메시 이웃, `IWANT`에 대한 답, 또는 홈 피어 -> 구독한 클라이언트 | 토픽 키(33), 개수(1)와 레코드. 각각 레코드 종류(1: `1` 방, `2` 접속 상태, `3` 채팅 줄, `4` 로그아웃)와 와이어 형식. 답하지 않음 |
| 23 | `IHAVE` | 멤버 -> 메시 이웃이나 멤버, 홈 피어 -> 구독한 클라이언트 | 토픽 키(33), 개수(1, 0에서 32)와 레코드 ID(각 16). 어느 것도 메시 링크를 유지시키지 않음. 답하지 않음 |
| 24 | `IWANT` | 멤버 -> `IHAVE`를 보낸 쪽, 구독한 클라이언트 -> 홈 피어 | 토픽 키(33), 개수(1, 1에서 32)와 레코드 ID(각 16). `GOSSIP`으로 답함 |
| 25 | `PUBLISH_RECORD` | 클라이언트 -> 홈 피어 | 종류 코드가 붙은 레코드 하나: 클라이언트 자신의 접속 상태, 채팅 줄, 로그아웃 |
| 26 | `RECENT` | 클라이언트 -> 홈 피어 | 토픽 키(33), 플래그(1: 비트 0 기록). 등록한 클라이언트를 토픽에 구독시킵니다(또는 갱신). |
| 27 | `SEALED` | 플레이어 -> 대상 연결의 홈 피어 -> 대상 연결 | 대상 키(32), 대상 연결(8), 보낸 쪽의 임시 X25519 키(32), 봉인된 텍스트(2바이트 길이, 최대 512바이트). 홈 피어는 데이터그램 전체를 바꾸지 않고 그 연결의 등록에만 전달합니다. |

`OBSERVED_ADDRESS` 상태(`ObservedAddressStatus`): `2` TOKEN_REQUIRED, `3` REGISTERED, `4` UNREGISTERED, `5` FULL, `6` TOO_MANY_CONNECTIONS, `7` INVALID_NAME, `8` SIGNED_OUT(코드 `1`은 쓰지 않음).

`RESULT` 상태(`ResultStatus`): `1` ACCEPTED, `2` STALE(같거나 새로운 시퀀스가 저장되어 있음), `3` INVALID(잘못된 토큰, 피어가 참여하지 않는 토픽의 graft도), `4` NOT_REGISTERED, `5` LIMIT_REACHED(레코드 속도를 넘은 호스트, 가득 찬 메시, 최대 토픽 수도), `6` DELIVERED, `7` UNKNOWN_TARGET. 메시지 종류 코드 `11`은 쓰지 않습니다.

## 등록과 관찰된 주소

한 주소에서 온 첫 `REGISTER`에는 토큰이 없습니다. 피어는 16바이트 토큰(실행마다의 비밀로 만든 주소, 포트, 키의 HMAC-SHA256. 60초 구간 두 개 동안 유효)과 함께 `TOKEN_REQUIRED`로 답합니다. 증명된 `REGISTER`(와 모든 갱신)의 표시 이름과 스탬프 nonce가 피어의 난이도에서 보낸 쪽 키의 유효한 스탬프가 아니면 `INVALID_NAME`으로 거부하고 아무것도 등록하지 않습니다. 토큰을 담아 다시 보낸 `REGISTER`는 보낸 쪽의 연결을 관찰된 주소로 등록합니다(최대 4096개 등록, 최대 300초 동안 허용). 등록된 주소에서 온 연결의 갱신에는 토큰이 필요 없습니다. 등록한 연결만 게시, 목록 조회, 구독, 신호를 할 수 있고(`FIND_PEERS`와 `SEALED`는 길이 규칙 안에서 누구에게나 답함), 큰 응답은 등록된 주소에서만 받습니다. 클라이언트는 허용된 수명의 절반마다 갱신합니다. NAT 재매핑은 `TOKEN_REQUIRED`로 드러나고, 클라이언트는 새 주소에서 다시 등록합니다.

**연결**(`RegistrationStore`): 피어는 키의 연결마다(키, 연결 번호) 등록 하나를 두며, 키 하나에 살아 있는 연결은 최대 8개입니다. 피어가 가지고 있지 않은 연결의 증명된 등록은 그 키의 살아 있는 연결이 8개인 동안 `TOO_MANY_CONNECTIONS`로 거부합니다(만료된 연결이 먼저 자리를 내줌). 클라이언트는 재시도 시간 뒤에 다시 시도하므로, 비정상 종료한 세션의 자리는 그 등록이 만료될 때, 최대 300초 뒤에 비워집니다. 같은 연결이 새 주소에서 오면(NAT 재매핑) 등록을 옮기고 그 키의 다른 연결은 그대로 둡니다. 같은 키의 다른 연결의 주소에서 등록하는 연결은 그 연결을 대신합니다. 주소 하나는 소켓 하나이기 때문입니다. 연결의 등록된 주소에서 온 수명 `0`의 `REGISTER`는 그 연결만 지웁니다. 등록이 필요한 요청은 보낸 쪽 키의 어느 등록된 연결의 주소에서 와도 받으며, 그 연결로서 동작합니다. 그 연결이 게시하는 방은 그 연결을 밝혀야 하고(아니면 `INVALID`), 구독은 그 연결만의 것이며(키의 연결마다 자기 구독이 있음), 신호나 귓속말은 대상 연결을 밝히고 그 연결만 받습니다. `REGISTER`에는 연결 시작(세션이 시작된 에포크 밀리초)이 담깁니다. 그 키의 로그아웃 ([커뮤니티](#커뮤니티-presencerecord-chatlinerecord-signoutrecord-sealedmessage) 절)을 가진 피어는, 로그아웃이 유지하는 연결이 아니면서 로그아웃의 타임스탬프보다 먼저 시작한 연결을 `SIGNED_OUT`으로 거부하고, 그런 연결의 등록을 지우며, 로그아웃을 받아들일 때 가지고 있던 그런 등록을 모두 버립니다. 그 클라이언트는 그 뒤 어디에도 다시 등록하지 않습니다. 클라이언트는 무작위 대상의 패딩된 `FIND_PEERS`(카드 없음)로 노드에게 다른 노드를 묻고, 알게 된 것을 공유 피어 파일([파일](#파일) 절)에 기록합니다. 모든 노드에 첫 등록 뒤 한 번, 그리고 클라이언트가 아는 학습한 피어가 8개보다 적은 동안 목록의 노드에 다시 묻습니다. 마지막 응답 30초 뒤에 시작해 간격을 매번 두 배로 늘리며, 세션당 최대 8번입니다. 그래서 노드들이 아는 피어가 적을 때 시작한 세션도 나중에 참가한 피어를 알게 됩니다.

## 피어 계층 (`PeerRouting`, `RoutingTable`, `PeerLookup`)

**증명**: 피어는 시드, 후보(주소가 증명되지 않은 hello나 조회 요청을 보낸 쪽), 기억한 피어, 조용한 아는 피어에게 패딩된 `HELLO` 요청으로 인사하며, 라운드(5초)마다 두 개씩 보냅니다. 인사한 주소에서 온 응답이 그 피어의 주소와 키를 증명합니다. 자기 주소에서 `FIND_PEERS` 요청에 답한 피어도 증명됩니다. 시드에는 키가 없습니다. 그 주소에서 온 첫 올바른 서명의 응답을 신뢰합니다(응답에는 기다리는 무작위 요청 번호가 있어야 함). 키를 고정한 시드는 아는 피어로 인사하므로 그 키의 응답만 인정합니다. 모든 카드와 `PEERS` 항목의 증명을 확인하며, 항목은 IPv4 주소이고 답하는 피어의 주소와 같은 종류(공인, 또는 로컬 네트워크와 루프백)일 때만 씁니다.

**라우팅 테이블**: ID의 공통 접두사에 따른 Kademlia k-버킷, 버킷당 피어 8개, 버킷당 증명된 피어 4개의 교체 캐시. 카드가 도달 가능이라고 하는 피어(자체 시험으로 확인된 피어)만 들어갑니다. 네트워크 한계: 같은 IPv4 /24(IPv6 /48)는 버킷당 2개, 테이블당 8개, 같은 IPv4 /16(IPv6 /32)은 테이블당 16개. 루프백 주소는 제한하지 않습니다. 가득 찬 버킷은 자기 피어를 유지합니다(오래 산 피어를 선호). 피어는 연속 두 번 답하지 않으면(조회 요청, 또는 10분 침묵 뒤의 hello) 빠지고, 한계를 지키는 가장 최근의 캐시 피어가 그 자리를 차지합니다. 증명된 리프(와 자리가 없는 전체 피어)는 테이블 밖에서 알려져 있습니다(최대 256개, 60초 침묵하면 빠짐). 자체 시험이 이들을 쓰고, 테이블이 비어 있는 동안은 토픽 계층도 씁니다. `FIND_PEERS`의 답으로 주거나 기억하지는 않습니다.

**조회**: 반복 조회이며 경로당 3개의 요청을 동시에 보내고, 경로에서 가장 가까운 피어 8개가 답하거나 실패할 때까지 계속합니다(요청당 2초와 재전송 한 번, 조회당 30초, 동시에 최대 8개 조회). 서로 겹치지 않는 경로를 쓰는 조회(소유자가 요청한 조회는 기본 3개, `MeshPeer.findPeers`)는 시작 피어를 경로에 차례로 나누어 주고, 응답에 나온 피어는 다른 경로가 이미 알고 있지 않으면 요청한 경로에만 들어갑니다. 경로 하나는 같은 /16에서 최대 2개의 피어만 고려합니다. 피어는 테이블에 피어가 생기고 첫 자체 시험이 끝나면 자기 ID 조회로 참가하고, 자체 시험으로 도달 가능이 확인되면 다시 합니다(요청의 도달 가능 플래그 덕분에 요청받은 피어가 이 피어를 테이블에 넣음). 테이블의 피어가 8개보다 적은 동안은 30초마다, 그 밖에는 10분마다 무작위 버킷을 갱신합니다.

**부트스트랩**(`KnownNodes` 위의 `PeerBootstrap`, 런처의 노드와 헤드리스 노드): 시드(단일 시드 규칙: 사용자가 저장한 노드 목록, 없으면 함께 배포된 `seeds.json`. 노드의 `--peer` 옵션. 런타임 실행의 `--seeds`와 `--seed`)와 가장 좋은 학습한 피어 32개(`peers.json`: 최근 성공이 먼저, 그다음 오래 알려진 순, 다른 것보다 먼저 /24당 최대 2개)에 함께 인사합니다. 먼저 답하는 쪽이 피어를 연결합니다. 피어는 5분마다, 그리고 멈출 때 라우팅 테이블의 전체 피어를 `peers.json`에 기록합니다. 런타임 세션은 자신을 등록한 노드, 내장 피어의 전체 피어, 목록의 노드가 알려 준 노드를 기록합니다. 학습한 피어는 시도했는데 연속 3번의 시작에서 답하지 않았을 때, 다른 키가 그 주소에서 답할 때, 마지막 성공 뒤 30일이 지났을 때 빠집니다.

## 도달성 자체 시험 (`ReachabilityCheck`)

피어는 무작위로 고른 아는 피어 최대 둘(도우미)에게 핑처럼 패딩한 `DIAL_BACK`을 요청합니다. 도우미는 카드의 증명이 유효한 요청자에게만 서비스합니다. 요청자의 관찰된 주소를 담아 요청을 무작위로 고른 아는 제3 피어에게 전달하고 그 주소로 답하거나, 아는 제3 피어가 없으면 주소 없이 답합니다. 둘 다 패딩된 요청보다 짧습니다. 제3 피어는 증명된 주소에서 알려진 도우미에게만 서비스하며, 지정된 주소로 `PROBE` (전달된 요청보다 짧고, 동시에 최대 4개, 그 뒤 IP 주소 하나에 초당 1)를 보냅니다. 기다리는 다이얼백의 프로브나 패딩된 `HELLO` 요청이 자기 소켓이 보낸 적 없는 주소(IP 주소 기준. 루프백 주소에서는 포트 기준. 최대 4096개 주소를 10분 동안 기억)에서 도착하면 요청자는 도달 가능(전체 피어)입니다. 받아들인 다이얼백의 프로브가 10초 안에 도착하지 않으면 다음 시험이나 요청하지 않은 hello가 달리 증명할 때까지 도달 불가(리프)입니다. 도달 가능은 유지합니다. 다른 결과는 받아들인 시험 5분 뒤에, 도우미가 아무도 받아들이지 않았거나 프로브가 피어가 보낸 적 있는 주소에서 왔으면 30초 뒤에 다시 시험합니다. 리프 전용 피어는 처음부터 도달 불가이며 시험을 요청하지 않습니다.

도우미의 응답과 제3 피어의 프로브는 모두 요청이 온 주소로 갑니다. 출발지를 위조하면 요청자는 요청 하나로 두 호스트가 피해자에게 보내게 할 수 있습니다(요청 바이트의 약 1.1배, 프로브는 IP 주소별 속도 제한). 프로브가 곧 시험이므로 그대로 둡니다.

## 토픽 (`TopicKey`, `TopicSwarms`, `TopicDirectory`, `Swarm`)

토픽 키는 종류(1: `1` MOD, `2` CHANNEL, `3` PLAYER)와 `BLNK topic 1\0`, 종류 코드, 이름(UTF-8)의 SHA-256입니다. 모드 토픽의 이름은 모드 id이므로 모드의 모든 버전이 공유합니다. 채널 토픽의 이름은 공백을 정리하고 소문자로 바꾼 채널 이름(최대 32바이트)이며 모든 모드가 공유합니다. 플레이어 토픽의 이름은 16진수로 쓴 키입니다. 해시는 라우팅 공간의 위치이며, 거기에 가장 가까운 전체 피어가 그 토픽의 저장 피어입니다. 피어는 소유자나 등록한 클라이언트 하나가 토픽을 쓰는 동안(그 피어를 통해 게시한 방이나 레코드, 목록 조회, 구독. 토픽을 새로 찾은 `LIST_ROOMS`는 첫 참가를 최대 2초 기다림) 토픽에 참여하며, 마지막 사용 10분 뒤에 떠납니다. 단, 그 피어를 통해 게시한 만료되지 않은 레코드나 구독한 클라이언트가 남아 있으면 떠나지 않습니다. 토픽은 최대 256개입니다.

**참가**: 피어는 서로 겹치지 않는 경로 3개로 저장 피어를 조회하고(라우팅 테이블이 비어 있으면 아는 피어에게 대신 물음), 각각에 `GET_TOPIC`으로 묻고, 응답의 토큰으로 `ANNOUNCE`해 자신을 알립니다. 저장 피어는 알림을 10분 동안 보관하며, 토픽당 멤버 최대 64명(새 멤버는 무작위로 고른 둘 중 오래된 쪽을 대신함), 토픽 2048개까지입니다. 멤버는 4분마다, 메시가 비어 있는 동안은 30초마다 토픽을 다시 조회하고 알립니다. `GET_TOPIC`에는 저장 피어가 알림으로, 멤버가 아는 멤버로 답합니다(피어 교환). 최대 16개이며 도달 가능한 멤버가 먼저입니다. 토큰(16바이트, `REGISTER`와 같음)이 묻는 쪽의 주소를 증명하므로, 누구도 다른 호스트의 주소를 알리거나 graft할 수 없습니다.

**메시**: 멤버는 메시 이웃이 6개가 될 때까지 멤버를 graft하고(도달 가능한 멤버가 먼저. 토큰이 없는 멤버에게는 먼저 `GET_TOPIC`으로 물음), 4개 아래면 더 graft하고, 12개를 넘으면 6개까지 prune합니다(먼저 자신을 graft한 이웃을). 이웃 중 적어도 2개는 자신이 직접 graft한 멤버입니다. 다른 쪽의 graft는 10개(12에서 그 몫을 뺀 수)까지 받고, 직접 graft한 이웃이 2개보다 적은 동안 graft합니다. 그래서 먼저 graft해 오는 멤버들이 피어의 메시 전체를 채울 수 없고, 거부된 graft는 다른 멤버에게 갑니다. 60초 동안 소식이 없는 이웃은 빠집니다. 30초 동안 트래픽이 없는 링크에는 빈 `IHAVE`를 보내 리프의 NAT 매핑을 열어 둡니다.

**가십**: 새 레코드는 즉시 모든 메시 이웃과 모든 구독한 클라이언트에게 갑니다(`GOSSIP`). 라운드(5초)마다 지난 라운드 이후 받아들인 레코드의 ID를 메시 이웃과 도달 가능한 다른 멤버 6개에게, 최근 두 라운드의 ID를 구독한 클라이언트에게 보내고(`IHAVE`), 받는 쪽은 아직 못 본 것을 요청합니다(`IWANT`). 새 메시 이웃은 모든 레코드의 ID를 받습니다. 레코드 ID는 `BLNK record 1\0`과 레코드의 와이어 형식 전체의 SHA-256 앞 16바이트입니다.

**레코드 확인**, 이 순서로: 레코드는 메시 이웃과, 요청을 받은 멤버에게서만 받습니다. 레코드 ID를 전에 보지 않았어야 합니다. 토픽과 그 종류가 그곳에 속하는지(모드 토픽의 방, 채널 토픽의 채팅 줄, 플레이어 토픽의 접속 상태는 그 플레이어가 보낸 것만, 로그아웃은 그 플레이어 자신의 토픽에서만). 시퀀스(오래된 것은 버림). 서명(속도보다 먼저. 위조된 레코드가 작성자의 속도를 쓰지 못하게). 종류별 작성자 속도(방: 순간 8, 그 뒤 초당 1. 채팅 줄: 순간 5, 그 뒤 초당 1, 그리고 5초보다 오래된 줄, 곧 기록의 줄은 기록 허용량 32에서, 그 뒤 초당 1. 채널에 참가한 피어가 기록을 받을 수 있게 하기 위함. 접속 상태와 로그아웃은 함께: 순간 16, 그 뒤 5초당 1. 50초마다 갱신하는 플레이어의 연결 8개가 들어가게 하기 위함). 레코드 표시 이름에 대한 작성자의 스탬프(접속 상태와 채팅 줄). 만료와 수명(방 저장소: 토픽당 512개, 호스트 키당 8개와 호스트 연결당 4개, 최대 600초 뒤. 커뮤니티 저장소: 접속 상태 256개, 플레이어의 연결마다 가장 새로운 것, 플레이어당 최대 8개 연결(새 연결은 먼저 만료되는 그 플레이어의 연결 자리를 차지하며, 그 연결이 더 일찍 만료될 때만), 최대 300초 뒤. 가장 새로운 채팅 줄 32개, 최대 30초 뒤의 날짜, 5분 보관. 플레이어의 가장 새로운 로그아웃, 최대 300초 뒤, 최대 30초 뒤의 날짜). 실패한 확인은 모두 세고 벌점을 줍니다([수신](#수신) 절).

## 방 (`RoomAdvertisement`, `RoomDescription`, `RoomKey`)

광고(레코드 종류 1)는 모드 토픽의 레코드이며 호스트가 서명합니다. 플래그(1, 비트 0 철회), 토픽 키(33), 호스트 키(32), 호스트 연결(8: 방을 가진 호스트 세션의 연결), 방 번호(4), 시퀀스(4), 만료(에포크 ms, 8), 설명, 호스트의 홈 피어(개수 1, 최대 3, 항목은 키 32 + 주소: 호스트의 연결이 처음 등록한 노드들), 호스트의 안정된 네트워크 좌표(플래그 1: `0` 없음, `1` 좌표(16)가 뒤따름. 철회에는 없음), 그리고 도메인 `Beacon.Link room advertisement 1\0`과 앞의 모든 바이트에 대한 호스트의 Ed25519 서명입니다. 홈 피어와 좌표를 빼고 최대 545바이트입니다(IPv6 항목 셋이면 716). 설명: 모드 지문(길이 바이트, 1에서 192바이트: 모드 정체성의 와이어 형식이며, 호스트의 모드 id와 버전, 엔진 버전을 밝힘), 방 이름과 맵 이름(텍스트, 각 최대 48바이트, 방 이름은 비어 있지 않음), 플레이어 수와 정원(각 1. 플레이어 수는 정원 이하, 정원은 1 이상), 방 플래그(1: 비트 0 비공개, 비트 1 게임 시작됨, 나머지 비트 0), 비공개 방의 참가 키(32, 비공개 방만), 모드 데이터(길이 바이트, 최대 64바이트, 그리고 바이트).

**모드 데이터**(`RoomSettings.getModData`): 호스트의 모드가 방과 함께 게시하고, 검색하는 클라이언트의 모드가 목록의 방에서 읽는 바이트입니다. 피어와 클라이언트는 읽지 않고 나릅니다. 모드가 자기 모드 데이터를 정의하고 문서화합니다. 데모는 1바이트, 방의 턴 속도를 게시합니다 (`DemoLobby`).

방 키(`RoomKey`)는 호스트 키 + 호스트 연결 + 방 번호입니다. 그래서 계정 하나의 두 연결이 나란히 방을 열 수 있고, 참가 요청은 방을 가진 연결에 닿습니다. 더 높은 시퀀스가 낮은 것을 대신합니다. 철회는 만료될 때까지 남아 있어 가십이 방을 되살리지 못합니다. 호스트는 40초마다 120초 만료로 갱신합니다. 피어는 토픽, 서명, 만료, 호스트의 속도만 확인하고 토픽의 방을 나열합니다. 클라이언트는 자기 모드 정체성(지문)의 방과 모드의 다른 버전의 방을 구별해, 후자는 그 호스트가 줄 거부 사유와 함께 따로 나열하고, 모든 방의 모드 id와 버전을 지문에서 읽어 보여 줍니다. 클라이언트의 모드 정체성으로 실행 중이고, 빈자리가 있고(플레이어 수가 정원보다 적음), 게임이 시작되지 않은 방에 참가할 수 있습니다. 나머지는 닫힌 방이며, 방 목록에서 흐리게 보이거나 숨겨집니다.

**비공개 방**: 비밀번호가 있는 방에는 호스트가 그 방을 위해 만든 X25519 참가 키 쌍의 공개 절반이 담깁니다. 비밀번호 자체는 보내지 않습니다. 참가자는 제안([신호](#신호-channelsignal) 절)에서 이를 증명합니다. 증명 = HMAC-SHA256(키 = 제안의 임시 키와 참가 키의 X25519 비밀, `SC4J Beacon.Link room password 1` || 호스트 키 || 방 번호(4) || 참가자 키 || 비밀번호의 UTF-8 바이트). 호스트는 참가 키의 개인 절반으로 같은 비밀을 합의하고, 올바른 증명이 없는 제안을 거부합니다(`WRONG_PASSWORD`). 중계 노드는 비밀도 비밀번호도 모르므로 증명에 대고 비밀번호를 시험해 볼 수 없고, 증명은 그 제안에만 맞습니다. 호스트와 공유하는 노드가 없는 참가자는 호스트의 홈 피어에 등록하므로 (학습하거나 기억하지는 않음), 제안과 호스트의 응답이 피어 하나를 거쳐 갑니다.

## 커뮤니티 (`PresenceRecord`, `ChatLineRecord`, `SignOutRecord`, `SealedMessage`)

**접속 상태**(레코드 종류 2): 플래그(1, 0), 토픽 키(33), 플레이어 키(32), 연결 번호(8), 스탬프 nonce(8), 시퀀스(4), 만료(8), 내용: 표시 이름(텍스트, 최대 32. 스탬프가 묶는 이름), 모드 id(텍스트, 최대 48. 런처는 `sc4j-launcher`, `BeaconLink.LAUNCHER_MOD_ID`), 모드 버전(텍스트, 최대 24), 모드 지문 SHA-256의 앞 8바이트(함께 플레이할 수 있는 플레이어끼리 같음), 상태(1: `1` 대기 중, `2` 자리 비움, `3` 방에 있음, `4` 게임 중), 자리 비움 문구(텍스트, 최대 32. 없거나 자리 비움이 아니면 빈 값. 다른 사람의 사용자 목록과 그 플레이어에게 귓속말한 뒤에 보임), 채널 이름(텍스트, 최대 32, 없으면 빈 값), X25519 귓속말 키(32, 세션마다 만듦), 홈 피어(방과 같음: 연결이 처음 등록한 노드들), 연결의 안정된 네트워크 좌표(방과 같음. 추가 레코드가 생기지 않도록 50초 갱신 때만 새로 함), 그리고 `Beacon.Link presence 1\0`과 앞의 모든 바이트에 대한 플레이어의 서명입니다. 플레이어의 모든 연결(런처, 게임, 다른 컴퓨터)은 자기 접속 상태에 서명해 모드의 토픽, 참가한 모든 채널, 플레이어 자신의 토픽에 게시하고, 120초 수명으로 50초마다 갱신하며, 내용이 바뀌면 바로 다시 서명합니다. 채널을 떠나거나 세션을 닫으면 5초 뒤 만료되는 접속 상태를 보냅니다. 오프라인으로 보이게 한 연결은 아무것도 게시하지 않습니다(계정 전체의 "오프라인으로 표시"는 없음). 저장소와 클라이언트는 연결(키와 연결 번호)마다 가장 새로운 접속 상태를 보관하므로, 플레이어 하나의 연결들이 나란히 있습니다.

**합친 접속 상태**(`ClientCommunity`, 보는 쪽이 표시하는 것): 보는 쪽이 따르는 토픽에 연결 중 하나라도 살아 있는 접속 상태가 있으면 플레이어는 온라인입니다. 연결 중 상태 순위가 가장 높은 것이 표시할 상태, 모드, 자리 비움 문구를 정합니다. 순위: 게임 중, 방에 있음, 모드에서 온라인(런처가 아닌 모드에서 대기 중), 런처에 있음(모드 id `sc4j-launcher`로 대기 중), 자리 비움. 살아 있는 연결 수가 플레이어의 장치 수입니다. 사용자 목록은 각 플레이어를 합쳐서 한 번만 보여 줍니다. 그래서 런처에서 게임을 시작한 플레이어를 친구는 "런처에 있음"에서 "게임 중"으로, 게임이 끝나면 다시 돌아가는 것으로 보며, 오프라인으로는 보지 않습니다. 런처의 접속 상태가 게임의 것과 나란히 살아 있기 때문입니다.

**자기 플레이어 토픽**: 모든 연결은 자기 플레이어 토픽을 구독합니다(접속 상태도 그곳에 게시함). 그래서 계정의 다른 연결의 접속 상태(같은 방식으로 합치며, 자기 연결 포함)와 계정의 로그아웃을 봅니다.

**채팅 줄**(레코드 종류 3, 채널 토픽에만): 플래그(1, 비트 0 감정 표현), 토픽 키(33), 작성자 키(32), 스탬프 nonce(8), 작성자 시퀀스(4), 타임스탬프(8), 표시 이름(텍스트, 최대 32. 스탬프가 묶는 이름), 텍스트(텍스트, 1에서 255바이트), 그리고 `Beacon.Link chat line 1\0`과 앞의 모든 바이트에 대한 작성자의 서명입니다. 타임스탬프 5분 뒤에 만료됩니다.

**홈 피어**: 클라이언트가 처음 등록한 노드들(최대 3개)이 클라이언트 대신 그 토픽에 참여합니다. `PUBLISH_RECORD`(등록한 클라이언트가 자기 레코드를 보냄)는 레코드를 그 토픽에 넣습니다. `RECENT`는 클라이언트를 90초 동안 구독시키며(`RESULT` 값. 토픽당 구독자 최대 256), 클라이언트는 그 3분의 1마다 갱신합니다. 기록 플래그가 있으면 피어는 먼저 가지고 있는 접속 상태, 채팅 기록, 로그아웃을 보내 줍니다. 피어는 토픽의 새 레코드를 모두 구독자에게 보내고(`GOSSIP`) 라운드마다 최근 두 라운드의 ID를 보내며(`IHAVE`), 구독자는 놓친 것을 `IWANT`로 요청합니다. 그래서 토픽의 메시는 도달 가능한 피어 사이에서만 돌고, NAT 뒤의 클라이언트에게는 다른 플레이어의 클라이언트로 가는 링크가 필요 없습니다(채팅에 리프끼리의 링크 없음). 홈 피어가 `NOT_REGISTERED`로 거부한 줄(예: NAT 재매핑 뒤 클라이언트의 등록을 잃음)은 토픽과 홈 피어마다 최대 8개까지 보관하고(가장 오래된 것이 자리를 내줌), 피어가 클라이언트를 다시 등록하면 보낸 순서대로 그곳에 다시 게시합니다. 줄은 작성자에서 그 홈 피어로, 읽는 쪽의 홈 피어가 다르면 메시를 거쳐, 거기서 읽는 쪽으로 갑니다. 그 길에서 라운드나 폴링 간격을 기다리는 곳은 없습니다. 클라이언트는 푸시된 모든 레코드를 중계자처럼 확인하고(토픽, 종류, 만료, 스탬프, 서명) 이미 본 레코드 ID는 버립니다. 작성자 속도는 홈 피어를 믿습니다.

**귓속말**(`SEALED`): 보내는 쪽은 대상의 살아 있는 연결마다, 그 연결의 가장 새로운 접속 상태를 보고 복사본 하나씩 봉인합니다. 새 X25519 키 쌍과 그 연결의 귓속말 키로 비밀을 합의하고, 일회용 키를 유도하고(HKDF-SHA256, 솔트는 `SC4J Beacon.Link whisper 1`의 SHA-256, 두 플레이어 키와 두 X25519 키), 타임스탬프(8)와 텍스트(텍스트, 최대 255)를 ChaCha20-Poly1305로 봉인합니다(nonce 0, 두 플레이어 키를 연관 데이터로). 서명한 각 복사본은 대상 연결을 밝혀 그 연결의 각 홈 피어로 보냅니다(그 연결의 복사본이 전달되거나 모든 홈 피어가 거부할 때까지 1초마다 4번 재전송). 지정된 연결의 등록을 가진 홈 피어는 복사본을 바꾸지 않고 그 연결에만 전달하고 `DELIVERED`로 답하며, 그 밖에는 `UNKNOWN_TARGET`으로 답합니다. 복사본 하나가 전달되면 귓속말은 전달된 것이고(나머지 복사본도 계속 보내 모든 연결이 받게 함), 모든 복사본이 거부되거나 시도 횟수를 다 쓰면 오프라인입니다. 누구나 보낼 수 있으며(주소와 키 속도가 제한함), 답은 요청보다 길지 않습니다. 홈 피어는 보낸 사람, 대상, 크기만 봅니다. 오프라인 대상을 위해 저장하는 것은 없습니다.

**다른 곳에서 모두 로그아웃**(레코드 종류 4, `SignOutRecord`, `BeaconLinkSession.signOutOtherDevices`): 플래그(1, 0), 플레이어 자신의 토픽 키(33), 플레이어 키(32), 유지할 연결(8: 이 레코드에 서명한 연결), 시퀀스(4), 타임스탬프(8, 에포크 ms), 만료(8, 타임스탬프 240초 뒤. 피어는 최대 300초 뒤까지 받음), 그리고 `Beacon.Link sign out 1\0`과 앞의 모든 바이트에 대한 플레이어의 서명입니다. 스탬프는 없습니다. 서명한 연결이 홈 피어를 통해 플레이어 자신의 토픽에 게시합니다(`PUBLISH_RECORD`. 나중에 그 연결을 등록하는 홈 피어도 받음). 자기 플레이어의 유효한 로그아웃(자기 토픽으로 푸시됨)을 받은 연결은, 그것이 다른 연결을 유지할 연결로 밝히고 타임스탬프가 자기 연결 시작보다 뒤이면 `LinkFailure.SIGNED_OUT`으로 세션을 끝냅니다. 채널을 닫고, 방을 철회하고, 떠나는 접속 상태를 보내고, 등록을 해제하고, 어디에도 다시 등록하지 않습니다. 로그아웃을 가진 노드는 그런 연결을 버리고 거부합니다([등록과 관찰된 주소](#등록과-관찰된-주소) 절). 푸시를 놓친 연결을 위한 안전장치이며, 레코드가 살아 있는 동안 다음 등록 갱신, 곧 등록 수명의 절반(150초) 안에 거부됩니다. 타임스탬프 뒤에 시작한 연결은 영향을 받지 않습니다. 따르는 플레이어 토픽(자기 것이나 친구의 것. 서명한 연결은 자기 것을 바로)에서 유효한 로그아웃을 받은 모든 클라이언트는 그것이 끝내는 연결의 접속 상태를 모든 토픽에서 바로 버립니다. 유지할 연결이 아니면서 접속 상태 시퀀스(초)가 타임스탬프의 초 이하인 모든 연결입니다. 로그아웃이 살아 있는 동안은 그 뒤의 접속 상태도 버리며, 끝난 연결의 떠나는 접속 상태도 포함합니다. 그래서 친구와 유지된 연결은 접속 상태가 만료될 때가 아니라 바로 장치 수가 줄어드는 것을 봅니다. 한계: 세션을 끝낼 뿐, 도난당한 키를 무효로 하지는 않습니다(새 계정이 필요합니다).

**무시 목록**(`CommunitySession.ignore`, `getIgnored`): 계정의 무시(차단)한 플레이어 목록이며, 계정의 모든 프로세스가 `blocked.json`([파일](#파일) 절. 게스트는 메모리에)으로 공유합니다. 무시한 플레이어의 채팅 줄과 귓속말은 전달되지 않고, 그 방은 모드가 숨깁니다. 이 목록은 네트워크로 나가지 않습니다.

## 네트워크 좌표 (`NetworkCoordinate`, `CoordinateReport`, `CoordinateEstimator`)

모든 호스트는 Vivaldi로 지연 공간에서 자기 위치를 추정합니다(3차원과 높이. 두 호스트의 추정 왕복 시간은 두 점의 거리에 두 높이를 더한 값). 좌표는 16바이트입니다. 세 성분과 높이이며, 각각 부호 있는 32비트 정수로 센 밀리초입니다(성분은 원점에서 10,000 ms 안, 높이는 0에서 10,000 ms. 읽는 쪽은 그 밖의 값을 거부하며, 가장 작은 int도 거부). 좌표 보고는 여기에 오차를 더합니다(1바이트, 100분의 1 단위, 최대 150: 호스트 추정치의 이동 상대 오차. 아무것도 모르는 호스트는 1.5). 카드(`HELLO`, `FIND_PEERS`, `DIAL_BACK`, `ANNOUNCE`, `GRAFT`), `PEERS`, `OBSERVED_ADDRESS`에 보낸 쪽의 보고가 담깁니다. 좌표만을 위한 메시지는 보내지 않습니다.

**표본**: 피어는 `HELLO` 요청(후보와 조용한 피어에게)과 조회 요청마다 왕복 시간을 재고, 응답에서 답한 피어의 보고를 가져옵니다. 클라이언트는 재전송하지 않은 노드 요청에 답이 오면 그 왕복 시간을 재고, 그 노드의 마지막 `OBSERVED_ADDRESS`나 `PEERS` 응답의 보고를 씁니다. 런타임 세션과 내장 피어는 추정기 하나를 함께 씁니다(소켓 하나, 위치 하나). 표본 하나는 측정 시간과 추정 시간의 차이에, 두 오차 중 자기 오차의 비율과 0.25를 곱한 만큼 좌표를 옮깁니다(오차도 같은 가중치로 표본의 상대 오차를 따라감). 높이는 0.1 ms 이상으로 유지하고, 5초를 넘는 표본은 무시하며, 원점으로 약하게 당겨 네트워크의 좌표가 떠내려가지 않게 합니다. 원격 호스트 하나는 5분마다 최대 표본 하나만 줍니다(최근 64개를 기억). 그래서 클라이언트의 몇 안 되는 노드가 다른 것들을 압도하지 않습니다. 서로 다른 호스트 6개의 표본으로 오차가 0.6 이하가 되면 좌표가 안정됩니다. 안정된 좌표만 방 광고와 접속 상태에 들어가며, 방의 호스트나 플레이어까지의 추정 (`LatencyEstimate`: 100 ms까지 good, 200 ms까지 fair, 그 위는 poor)은 어느 한쪽에 좌표가 없으면 알 수 없음입니다.

**이상값**: 원격 호스트는 와이어 한계 안에서 자기 좌표와 오차를 속이거나 응답을 늦출 수 있습니다. 안정된 좌표는 측정 시간과 추정 시간이 4배보다 더 차이 나는 표본을 받지 않습니다(피어는 이를 `COORDINATE_OUTLIER`로 세고 원격 호스트에 벌점 1점). 이런 이상값이 연달아 오면 8번째마다 받아들이므로, 실제로 옮겨 간 호스트는 오차가 커져 더 이상 안정되지 않게 되고 다시 표본을 따라갑니다.

**개인 정보**: 레코드의 좌표는 지연 공간에서 밀리초 단위 이상의 정보를 주지 않으며 주소를 담지 않습니다. 오프라인으로 보이는 플레이어는 접속 상태를 게시하지 않으므로 좌표도 게시하지 않습니다. 방의 좌표는 호스트의 것이며, 참가자는 어차피 호스트에 닿습니다.

## 참가자 사이의 채널 (`sc4j-beaconlink`, `channel` 패키지)

### 신호 (`ChannelSignal`)

`SIGNAL`의 페이로드: 종류(1), 보낸 쪽의 연결 번호(8), 필드. 엔벨로프의 서명된 보낸 쪽 키와 그 연결이 신호를 보낸 참가자입니다. `SIGNAL`은 대상의 키와 연결을 밝히므로, 참가 요청은 보내는 대상인 호스트 연결과 제안의 방 번호로 방을 가리킵니다. 주소 후보는 개수(1, 최대 8)와 주소들입니다.

| 종류 | 보낸 쪽 연결 다음의 필드 |
|---|---|
| `1` OFFER | 시작하는 쪽의 수신 번호(8), X25519 임시 공개 키(32), 참가 플래그(1). 플래그가 `1`이면 방 번호(4), 참가자의 모드 정체성(길이 바이트와 바이트), 비공개 방의 비밀번호 증명(길이 바이트 `0` 또는 `32`와 바이트. [방](#방-roomadvertisement-roomdescription-roomkey) 절). 그다음 후보 |
| `2` ANSWER | 시작하는 쪽의 수신 번호(8), 응답하는 쪽의 수신 번호(8), 임시 공개 키(32), 후보 |
| `3` REFUSAL | 시작하는 쪽의 수신 번호(8), 사유(1): `0` 호스트가 그 방을 가지고 있지 않음, 그 밖에는 엔진 `JoinRefusal`의 코드(엔진 버전, 모드 정체성, 꽉 찬 방, `9` 틀린 비밀번호) |

신호의 엔벨로프는 보낸 쪽이 서명하고 대상을 밝히므로, 두 임시 키와 수신 번호는 두 정체성으로 인증됩니다. 두 참가자 중 키가 작은 쪽이, 계정 하나의 두 연결이면 연결 번호가 작은 쪽이 제안합니다(둘 다 부호 없이 비교). 참가자는 항상 제안합니다. 호스트는 아직 연결되지 않은 참가 요청을 최대 16개 보관하며, 새 요청이 가장 오래된 것의 자리를 차지합니다.

### 키 스케줄 (`ChannelKeys`)

transcript = SHA-256(`SC4J Beacon.Link channel 1` || 시작하는 쪽 정체성 || 시작하는 쪽 연결 || 응답하는 쪽 정체성 || 응답하는 쪽 연결 || 시작하는 쪽 임시 키 || 응답하는 쪽 임시 키 || 시작하는 쪽 수신 번호 || 응답하는 쪽 수신 번호). 그래서 채널의 키는 그 두 연결에 속하며, 어느 계정의 다른 연결에도 속하지 않습니다. PRK = HMAC-SHA256(key = transcript, X25519 비밀). key(시작하는 쪽 -> 응답하는 쪽) = HMAC-SHA256(PRK, `initiator to responder` || 0x01), key(응답하는 쪽 -> 시작하는 쪽) = HMAC-SHA256(PRK, `responder to initiator` || 0x01). 모두 0인 비밀은 거부하고, 비밀은 쓴 뒤 0으로 지웁니다.

### 데이터그램 (`ChannelDatagramUtils`, `ChannelCipher`, `ChannelFrame`)

`BLCH`(4) | 받는 쪽의 수신 번호(8) | 카운터(8) | 프레임의 ChaCha20-Poly1305 암호문 | 태그(16). 연관 데이터는 헤더 20바이트, nonce는 0 바이트 4개와 카운터입니다. 카운터는 방향마다 0부터 시작합니다. 256 카운터의 재전송 창을 복호화 전에 확인하고 인증 뒤에 기록합니다. 최대 1200바이트입니다. 채널 데이터그램은 클라이언트의 UDP 소켓을 엔벨로프와 함께 쓰며, 매직으로 구별합니다.

**프레임 타입**(`ChannelFrameType`): `1` PROBE, `2` PROBE_ACK(홀 펀칭), `3` DATA(최대 1024바이트), `4` PING, `5` PONG(2.5초마다 연결 유지, 지연), `6` CLOSE, `7` RELAY_QUERY, `8` RELAY_STATUS, `9` RELAY_FORWARD, `10` RELAY_DELIVER. 중계 프레임은 상대 참가자를 와이어 형식(40바이트)으로 밝힙니다. 직접 경로가 없는 쌍은 둘 모두와 직접 채널이 있는 다른 참가자를 쓰며, 측정한 지연이 가장 낮은 참가자를 고릅니다. A는 C에게 RELAY_FORWARD(B, 봉인된 A->B 데이터그램)를 보내고, C는 B에게 RELAY_DELIVER(A, 같은 바이트)를 보냅니다. 중계자는 이를 읽거나 바꿀 수 없고, 쌍마다 정해진 양까지만 전달합니다. 피어는 자신이 참여하지 않은 게임의 채널 데이터그램을 중계하지 않습니다.

### 오버레이 (`LinkOverlay`, `ChannelOverlay`)

오버레이 데이터그램은 포트 바이트와 최대 1023바이트이며, 참가자 단위로 주소를 정합니다. 포트 1에서 15는 엔진의 것입니다. `1` 엔진 로비 (네트워크 로비 3: 참가자 목록이 각 멤버의 참가자를 와이어 형식으로 밝힘), `2` 엔진 락스텝 전송(엔진 로비를 쓰는 모든 모드). 포트 16에서 255(`LinkOverlay.FIRST_MOD_PORT`부터)는 모드 자체의 프로토콜에 쓸 수 있으며, 모드마다 자기 포트를 문서화합니다.

## 파일

- `<install>/launcher/seeds.json`(런처와 함께 배포되며 릴리스마다 바뀜)과 `<install>/userdata/beaconlink/nodes.json`(사용자의 노드 목록. 사용자가 저장하면 런처가 쓰고 런타임에 `--seeds`로 넘김. 이 파일이 생기기 전까지 런처의 편집기와 노드는 `seeds.json`을 대신 쓰고 넘김; `NodeListFile`): `{"format": 1, "nodes": [...]}`, 항목은 `"host:port"`(어느 키든) 또는 `{"address": "host:port", "key": "<64 hex digits>"}`(키 고정, 고급 옵션). 최대 64 KiB, 중첩 최대 8. IPv6 호스트는 대괄호로.
- `<install>/userdata/beaconlink/node.json`(런처 노드의 설정): `{"format": 1, "role": "automatic", "port": 7455}`. 역할은 `automatic`(포트에서 수신, 자체 시험이 통과하면 전체 피어) 또는 `off`(빈 포트에서 리프 전용). 없으면 7455에서 자동.
- 공유 파일(`SharedFile`): 한 컴퓨터의 여러 프로세스(런처의 노드, 모든 게임, 자기 폴더의 헤드리스 노드)가 파일 하나를 동시에 씁니다. 쓰는 쪽은 파일 자체를 읽기-쓰기로 열고, 파일 전체의 배타 잠금을 잡고, 읽고, 자기 변경을 병합하고, 결과를 처음부터 그 자리에 쓰고, 나머지를 잘라 내고, 디스크에 강제로 기록하고, 잠금을 풉니다. 읽는 쪽은 공유 잠금을 잡습니다. 이름 바꾸기, 임시 파일, 백업 파일은 없습니다. 없거나 빈 파일은 아무것도 담지 않습니다. 손상된 파일(쓰는 도중 끝난 쓰는 쪽)은 경고 하나와 함께 아무것도 담지 않은 것으로 보고, 다음 병합이 다시 씁니다. 각 프로세스는 병합 결과를 자기 뷰로 삼으므로 다른 프로세스가 추가한 것을 봅니다.
- `<install>/userdata/beaconlink/peers.json`과 노드의 `<state>/peers.json`(`PeerStore`, 공유 파일): `{"format": 1, "peers": [{"key": "<hex>", "address": "<IP literal>", "port": <port>, "firstSeen": <ms>, "lastSuccess": <ms>, "failures": <n>}, ...]}`, 최대 256개 피어, 최대 256 KiB. `lastSuccess` 0은 다른 노드가 알려 주었지만 답한 적 없는 피어입니다. 병합: 키 기준 합집합. 같은 키의 두 항목은 `lastSuccess`가 새로운 쪽이 주소, 포트, 실패 수를 정하고, `lastSuccess`가 같으면 `failures`가 큰 쪽입니다. `firstSeen`은 최솟값입니다. 한 주소의 두 키는 `lastSuccess`가 새로운 쪽이 남습니다. 실패가 3번이거나 30일보다 오래된(`lastSuccess`, 답한 적이 없으면 `firstSeen` 기준) 항목은 빠집니다. 목록은 `lastSuccess` 내림차순, `firstSeen` 오름차순, 키 오름차순으로 256에서 자릅니다. 프로세스는 마지막 병합 이후 자신이 바꾼 항목만 병합하므로, 다른 프로세스가 뺀 항목은 빠진 채로 남습니다. 5분마다, 그리고 멈출 때 병합하며, 리프는 쓰지 않습니다.
- `<install>/userdata/beaconlink/peer.key`, 노드의 `<state>/identity.key`: 위의 키 파일. 증명 nonce는 저장하지 않으며, 피어가 시작할 때마다 다시 찾습니다.
- `<install>/userdata/beaconlink/node.lock`: 노드를 실행하는 런처가 잠가 두는 빈 파일.
- `<install>/userdata/beaconlink/accounts/<id>/`(계정, [정체성](#정체성) 절): `identity.key`(플레이어 키), `account.json` (`{"format": 1, "name": "<name>", "difficulty": 24, "stamp": <nonce>, "lastUsed": <epoch ms>}`: 이름과 이름을 키에 묶는 플레이어 스탬프. 스탬프가 이름을 묶지 않는 폴더는 계정이 아님), `friends.json`(`PlayerListStore`, 공유 파일: `{"format": 1, "players": [{"key": "<hex>", "time": <ms>, "removed": false}, ...]}`. 키마다 가장 새로운 `time`이 이기고, 같은 시간이면 삭제가 이김. 친구를 아직 가진 프로세스가 되살리지 못하도록 삭제는 30일 동안 삭제 항목으로 남음. 목록은 최대 16명이며 가장 오래된 추가가 자리를 내줌. 자기 변경마다 바로 병합하고 10초마다 다시 읽음), `blocked.json`(무시한 플레이어. `friends.json`과 같은 형식과 규칙, 최대 256명), `account.lock`(계정을 쓰는 모든 프로세스가 공유 잠금으로 잡는 빈 파일).
- 토픽, 알림, 메시, 레코드, 등록, 구독, 귓속말 키, 벌점, 그레이리스트는 메모리에만 있습니다.

## 버전 관리

프로토콜 1이 유일한 프로토콜입니다. 엔벨로프의 버전 바이트는 `1`이며, 받는 쪽은 다른 버전을 버리고, 모르는 종류와 기능 비트는 버리거나 무시합니다. 1.0 전에는 프로토콜 번호, 레코드와 파일 버전, 해시와 서명 도메인의 번호가 모두 `1`이며, 필드 구조나 의미는 번호를 바꾸지 않고 바뀔 수 있습니다. 피어는 `HELLO`와 `PONG`에 소프트웨어 버전을 보냅니다 (`MeshPeer.SOFTWARE`, 현재 `sc4j-beaconlink-peer 0.11`). 이 값에 의존하는 규칙은 없습니다.

피어 계층은 IPv4만 라우팅합니다. 런타임의 세션 소켓(`UdpDatagramEndpoint`)이 IPv4이고, 프로세스당 소켓 하나가 필요합니다(피어가 관찰하는 주소가 홀 펀칭에 쓰는 주소여야 함). IPv6 주소의 `PEERS` 항목은 버리고 IPv6 시드에는 닿을 수 없습니다. 주소 인코딩과 /48, /32 네트워크 한계는 이미 IPv6를 다룹니다.
