# Beacon.Link protocol reference, protocol 1

**English** | [한국어](protocol.ko.md)

Beacon.Link lets SC4J players find each other through a network of peers that every SC4J runs (the launcher's node, the runtime's embedded peer, the headless node of the [operator guide](operator.md)) and play over encrypted channels between the players. Nobody runs a central server. This document describes the wire as it is: the peer and client messages (module `sc4j-beaconlink-protocol`), the receiving rules of peers and clients (module `sc4j-beaconlink-peer`, `MeshPeer`), the channel signals and datagrams between participants (module `sc4j-beaconlink`), and the files. The Javadoc of the named classes is the normative detail.

All integers are big-endian and unsigned unless stated. A datagram is at most 1200 bytes. Texts are UTF-8 with a one-byte length; invalid UTF-8 is refused. An address is its family (one byte, `4` or `6`), the 4 or 16 address bytes and the port (two bytes); no name is ever looked up while reading. Every reader refuses truncated fields, out-of-range values and trailing bytes without throwing.

## Identities

Every account has a player key (`accounts/<id>/identity.key`) and every peer a peer key (the launcher node's `peer.key`; the headless node's `<state>/identity.key`; a runtime run's embedded peer a key made for the run in memory). All are Ed25519 key pairs (JDK built-in); the 32-byte public key is the identity. The player key signs rooms, presences, chat lines, whispers and signals and is the player's identity (`LinkPlayer`), shown as `Name#abcd12` (the account's name and the first 6 hexadecimal digits of SHA-256 of the key, `IdentityKey.getTag`). A peer key is a routing identity only and is never shown. Keys are created by the launcher (a player key, for a new account) or at the first use (a peer key); users never type or paste one. Key files (`IdentityKeyFileUtils`): the magic `BLKF`, version `1`, the private key bytes and the public key bytes, written atomically through a temporary file of the folder, which on POSIX file systems the JDK creates readable by its owner only (`rw-------`), a mode the replaced file keeps. A new key is a new identity.

**Connections**: one account may be in use on several devices at once (the launcher, a game, another computer). Every client session is one connection of its account: at its start it draws a random connection number (8 bytes) and keeps it for its life, and the epoch millisecond of that start is its connection start. A participant (`LinkParticipant`) is the pair of the player key and the connection number, in its wire form the key (32) and the number (8): registrations, rooms, signals, channels, the overlay, the lobby and the lockstep transport address one participant, so that two connections of one account register, host rooms and hold channels side by side, even to each other. Friends, presences, chat lines, whispers and the ignore list are about the player (`LinkPlayer`). A connection number is no secret: registering any connection needs the player key and its stamp.

**Player names** (`PlayerNameUtils`, the one definition the launcher, the account store and every peer use): the typed name in Unicode NFC, without white space around it and with every run of white space inside it made one space; 1 to 32 UTF-8 bytes, no `#` and no control, format, private-use, surrogate or unassigned character. A valid name is its own normalized form. The name is fixed when the account is made: the player stamp binds it to the key (below), so another name is another account.

**Accounts** (`AccountStore`, `Account`): the launcher keeps the player accounts of an install, one folder per account named by its id (the first 16 hexadecimal digits of SHA-256 of the key; the tag starts it), with the key, the name and its player stamp, the friends and the ignored (blocked) players. No account is made on its own: the user creates one (a name, a random key and the stamp of both) or imports one, and chooses the account a game runs with; the launcher passes its folder to the runtime (`--account <dir>`). There is no rename. Every process that uses an account (a game, the launcher's session) holds a shared lock of its lock file (`AccountLock`): any number of them use one account at once, and the account cannot be deleted while one does (deleting takes the exclusive lock). A run without an account plays as a guest named `Guest` whose key and stamp live in memory for the run only. A backup file (`AccountBackup`, `.sc4jaccount`) carries an account to another install under its own name: the magic `BLKA`, version `1`, flags (bit 0: protected by a password), for a protected backup the salt (16), the PBKDF2-HMAC-SHA256 iteration count (4) and the AES-GCM nonce (12), then the body (name, stamp difficulty (1), stamp nonce (8), key file, friends and ignored players), encrypted with AES-256-GCM under the password's key with the header as associated data when protected. A backup whose stamp does not bind its name to its key, and any other file (a key file alone included), is refused.

**Game command line**: a runtime run takes its Beacon.Link only from its command line, never from the install layout: `--account <dir>` (the account folder; absent: a guest), `--seeds <file>` (a node list), `--seed <host:port>` (repeatable) and `--peers <file>` (the shared peers file; absent: learned peers are neither read nor kept). It offers Beacon.Link only when one of `--seeds`, `--seed` or `--peers` is given. The launcher passes the account folder, the seeds by the one seed rule (the user's `nodes.json` once saved, otherwise the shipped `seeds.json`) and the install's `peers.json`; a person starting a game by hand passes the same, or nothing. The run's embedded peer is a leaf with a key made for the run in memory, so two runs never share a peer key and nothing of it is kept. The launcher's node is the computer's long-lived peer: the first launcher of an install holds `node.lock` and runs the node with `peer.key`; a further launcher runs none and takes the node after the first closes.

**Peer ID** (`PeerId`): SHA-256 of the ASCII text `BLNK peer id 1`, the peer key and its proof nonce (8). The proof nonce is valid when SHA-256 of `BLNK peer proof 1`, the key and the nonce starts with 20 zero bits (the network's difficulty; a peer finds its smallest valid nonce at each start, about 0.1 s on a desktop core). So nobody chooses where an ID lies, and every ID costs work; a receiver checks the proof of every peer before it uses the peer's ID. IDs are compared by XOR distance (Kademlia).

**Player stamp** (`PlayerStamp`): a nonce whose SHA-256 hash of `BLNK player stamp 1`, the player key, the name's UTF-8 length (1), the name and the nonce (8) starts with 24 zero bits, and the name is a valid player name; found once per account, when the launcher creates it, and kept in `account.json`. Every registration, presence and chat line carries the name and the nonce; peers and clients check the stamp of the sender's key and the carried name, so a name the stamp does not bind is refused, and a key shows no other name without the work of a new stamp (as much as a new account).

## Roles

- Full peer: its reachability self-test proved that strangers reach its socket. Only full peers enter routing tables, `PEERS` answers, storing peer sets of topics and `peers.json`; they store topic announcements and form the topic meshes.
- Leaf: a peer whose self-test did not prove it (`NOT_VERIFIED` or `NOT_REACHABLE`). It looks up, greets and answers like any peer, and is known to the peers it talks to outside their tables; it promotes itself when a later test proves it.
- Leaf-only peer (`PeerConfiguration.isLeafOnly`): never a full peer, whatever arrives; its cards always say not reachable and it never asks for a dial-back. It still serves other peers' self-tests as helper and third peer. The launcher's node is leaf-only in the off role.
- Home peer: a peer at which a client connection registered (`REGISTER`). It tells the client its observed address, takes part in the client's topics for it, pushes it their records, relays signals between its registered connections and whispers to them. A client registers at up to 3 home peers (its first registered nodes). A runtime session is a client of its seeds and learned nodes and runs an embedded leaf peer on the same socket; the launcher's node and the headless node run alone on a socket of their own (`PeerSocket`, `PeerBootstrap.run`).
- Participant: one connection of a player in a room. Game traffic flows only on channels between participants (section [Channels](#channels-between-participants-sc4j-beaconlink-package-channel)); no peer carries it unless it is a participant of that game.

## Envelope (`Envelope`, `MessageEncoder`)

| Field | Bytes | Meaning |
|---|---|---|
| magic | 4 | `BLNK` |
| version | 1 | `1` |
| kind | 1 | message kind code (below) |
| flags | 1 | bit 0: reply (a reply is never answered); other bits zero |
| request number | 4 | chosen by the requester; a reply repeats it |
| timestamp | 8 | sender wall clock, epoch milliseconds (signed 64-bit) |
| nonce | 8 | random per message, also per resend |
| sender key | 32 | Ed25519 public key of the sender |
| body length | 2 | |
| body | n | kind-specific |
| padding length | 2 | |
| padding | p | zero bytes |
| signature | 64 | Ed25519 signature of the sender over every byte before it |

The header is 61 bytes, the trailer `2 + p + 64`. Every field is under the signature, but an envelope does not name its receiver: a signed datagram is valid at any peer, so receivers never let a copy act for its sender (the nonce check comes before the key's rate, and penalties graylist a key and an address alone only when the address is proved, section [Receiving](#receiving)).

**Request numbers**: the peer layer draws each request number at random (never one still waiting), so that nobody who saw one request can predict the next, for example to answer a seed's hello for the seed. The topic layer, the self-test and a client count up from a random start. A requester accepts a reply only with a waiting request number, from the address it asked and, when it knows one, with the key it expects.

**Padding**: requests to an address that has not proved itself (`PING`, `REGISTER`, `HELLO`, `DIAL_BACK`) are padded to 256 bytes, `FIND_PEERS` to 617 bytes (the longest `PEERS` answer), `GET_TOPIC` to 1155 bytes (the longest `TOPIC_PEERS` answer). A peer never answers an unproved address with more bytes than the request had: an answer that would be longer is not sent (counted `UNPADDED`). This covers the refusals too (`NOT_REGISTERED` to `PUBLISH_ROOM`, `LIST_ROOMS`, `SIGNAL`, `PUBLISH_RECORD`, `RECENT`; `INVALID` to `ANNOUNCE`, `GRAFT`).

## Receiving

### At a peer (`MeshPeer.receive`)

Checks in this order, the cheap ones before any signature work; whatever fails is dropped, counted and never answered:

1. length (at most 1200 bytes; `OVERSIZE`);
2. the rate of the source IP address (burst 256, then 128 per second; `ADDRESS_RATE`);
3. the graylist of addresses (`GRAYLISTED`);
4. the envelope structure and the body of its kind (`MALFORMED`); replies that only clients receive (`OBSERVED_ADDRESS`, `ROOM_LIST`; `UNEXPECTED_REPLY`); the peer's own key (`OWN_KEY`);
5. the timestamp window, 30 s around the receiver's clock (`OUTSIDE_WINDOW`);
6. the signature (`FORGED`);
7. the graylist of keys and of keys at addresses (`GRAYLISTED`);
8. the nonce: a (sender key, nonce) pair is remembered for twice the window, 65536 in all and at most 2048 of one source IP address; a full cache refuses new messages instead of forgetting (`REPLAYED`, `REPLAY_SOURCE_FULL`, `REPLAY_CACHE_FULL`);
9. the rate of the sender key (burst 32, then 16 per second; `KEY_RATE`), charged only for a fresh, validly signed message, so that forged or resent copies never spend another key's rate.

Then the handler of the kind runs. Handlers count what they do not use: `UNPADDED` (above), `NOT_A_PEER` (a peer message that does not come from a peer known at its address, or a reply to no waiting request), `INVALID_PROOF` (a card whose proof nonce is not valid), `INVALID_ENTRY` (an unused entry of a `PEERS` or `TOPIC_PEERS` answer, counted per entry), `UNREQUESTED_PROBE`, `NOT_IN_TOPIC`, `INVALID_RECORD` (per record), `COORDINATE_OUTLIER` (per sample, section [Network coordinates](#network-coordinates-networkcoordinate-coordinatereport-coordinateestimator)). A handler that throws is a defect of the peer: the datagram is lost, the exception logged and counted `DEFECT`; nothing reaches the owner's loop. The counts are logged when the peer stops (and every hour by the headless node).

### Penalties and graylist (`Graylist`)

| Penalty | Points |
|---|---|
| an invalid record: another topic or a kind that does not belong there, a bad signature or stamp, a too long lifetime | 10 |
| a card with a forged proof | 10 |
| a record over its author's rate | 2 |
| an expired record; a topic message from a peer outside the topic's mesh; a reply to no request; an unpadded request; a coordinate sample the settled coordinate rejects | 1 |

Points are counted per key and source address and forgotten 60 s after the last penalty. At 40 points that key at that address is graylisted for 10 minutes. If the address is proved for the key (a mesh neighbour grafted with its token, a routing contact that answered there, a registered client), the key alone and the address alone (the IP address, all ports; on loopback the socket address) are graylisted as well: every datagram from them is dropped before its signature is checked (the address) or right after (the key), and the peer leaves every mesh, member list and stored announcement. An unproved source address may be spoofed and a signed datagram may be resent from elsewhere, so neither may graylist another host. Penalties and the graylist are local; there is no shared reputation.

### At a client (`BeaconLinkClient`)

The session socket carries channel datagrams (magic `BLCH`, section [Channels](#channels-between-participants-sc4j-beaconlink-package-channel)) and envelopes. With an embedded peer, an envelope stays with the session only if it is a reply to a waiting session request from that request's node or to one of its whispers, a signal or a whisper for the session's key from one of its nodes, or a push of one of its nodes for a topic the peer does not take part in; everything else goes to the peer. The session takes:

- a reply: with a waiting request number, from the node it asked, inside the window, validly signed, with the node's key (a pinned key, or the key of the node's first answer in the session; another key marks the node as answering with the wrong key), and a fresh nonce;
- a signal: from a node it is registered at, for its own key and connection, not from its own participant (the sender key with the connection the payload names), inside the window, validly signed; only signals of channels it has or waits for and joins of rooms it holds are acted on and remembered against replay (per sender key);
- a push (`GOSSIP`, `IHAVE`, `SEALED`): from a node it is registered at, with the node's key (a whisper with its sender's key), inside the window, validly signed; every pushed record is checked as a relay checks it, and a whisper's nonce is remembered under its sender.

A datagram that fails is dropped and counted per source; a defect while handling one is logged and the poll goes on.

| Code | Kind | Direction | Body |
|---|---|---|---|
| 1 | `REGISTER` | client -> home peer | token (length byte, at most 32 bytes), lifetime seconds (2; `0` removes the registration of the connection), display name (text, at most 32 bytes), stamp nonce (8), mod fingerprint, connection number (8), connection start (epoch ms, 8), flags (1, all zero) |
| 2 | `OBSERVED_ADDRESS` | reply to `REGISTER` | status (1, below), observed address, granted lifetime seconds (2), token (length byte + bytes; with `TOKEN_REQUIRED`), the peer's coordinate report (17) |
| 3 | `PUBLISH_ROOM` | client -> home peer | a room advertisement without the withdrawn flag |
| 4 | `LIST_ROOMS` | client -> home peer | mod topic key (33), page offset (2) |
| 5 | `ROOM_LIST` | reply to `LIST_ROOMS` | total rooms of the topic (2), page offset (2), count (1) and advertisements |
| 6 | `WITHDRAW_ROOM` | client -> home peer | a room advertisement with the withdrawn flag |
| 7 | `SIGNAL` | client -> home peer -> client | target key (32), target connection (8), payload (two-byte length, at most 512 bytes); the home peer forwards the whole datagram unchanged to the registration of that connection only |
| 8 | `PING` | anyone -> peer; padded | empty |
| 9 | `HELLO` | peer <-> peer, request and reply; requests padded | card (proof nonce 8, flags 1: bit 0 reachable, coordinate report 17), capabilities (2, bit set: `1` answers `FIND_PEERS`, `2` takes part in topics; unknown bits ignored), software version (text, at most 32 bytes) |
| 10 | `FIND_PEERS` | peer -> peer, client -> peer; padded to 617 bytes | target ID (32), card flag (1: `0` none (a client), `1` a card follows) and the sender's card |
| 12 | `RESULT` | reply to `PUBLISH_ROOM`, `WITHDRAW_ROOM`, `LIST_ROOMS` (refusal), `SIGNAL`, `ANNOUNCE`, `GRAFT`, `PUBLISH_RECORD`, `RECENT`, `SEALED` | status (1, below), value (8: the lifetime in seconds of an accepted announcement or subscription, else `0`) |
| 13 | `PONG` | reply to `PING` | observed address, peer software version (text, at most 32 bytes) |
| 14 | `DIAL_BACK` | peer -> known peer -> third known peer, request and reply; the requester's request padded | the sender's card, nonce (8), address flag (1) and address: none in the requester's request and in a refusing reply, the requester's observed address in the forwarded request and in an accepting reply |
| 15 | `PROBE` | third peer -> requester's observed address | nonce (8); never answered |
| 16 | `PEERS` | reply to `FIND_PEERS` | the answering peer's coordinate report (17), count (1, at most 8) and entries: key (32), proof nonce (8), address; the full peers of the answering peer's routing table closest to the target, the asker left out |
| 17 | `GET_TOPIC` | peer -> storing peer or member; padded to 1155 bytes | topic key (33) |
| 18 | `TOPIC_PEERS` | reply to `GET_TOPIC` | topic key (33), address token (length byte, at most 32 bytes), member flag (1: the answering peer is in the topic), count (1, at most 16) and entries: key (32), proof nonce (8), address, reachable flag (1) |
| 19 | `ANNOUNCE` | member -> storing peer | topic key (33), the sender's card, the storing peer's token for the sender |
| 20 | `GRAFT` | member -> member | topic key (33), the sender's card, the other member's token for the sender |
| 21 | `PRUNE` | member -> mesh neighbour | topic key (33); never answered |
| 22 | `GOSSIP` | member -> mesh neighbour, answer to `IWANT`, or home peer -> subscribed client | topic key (33), count (1) and records, each its record kind (1: `1` room, `2` presence, `3` chat line, `4` sign-out) and its wire form; never answered |
| 23 | `IHAVE` | member -> mesh neighbour or member, home peer -> subscribed client | topic key (33), count (1, 0 to 32) and record IDs (16 each); none keeps a mesh link alive; never answered |
| 24 | `IWANT` | member -> sender of an `IHAVE`, subscribed client -> home peer | topic key (33), count (1, 1 to 32) and record IDs (16 each); answered with `GOSSIP` |
| 25 | `PUBLISH_RECORD` | client -> home peer | one record with its kind code: the client's own presence, chat line or sign-out |
| 26 | `RECENT` | client -> home peer | topic key (33), flags (1: bit 0 backlog); subscribes the registered client to the topic (or renews it) |
| 27 | `SEALED` | player -> target connection's home peer -> target connection | target key (32), target connection (8), the sender's ephemeral X25519 key (32), sealed text (two-byte length, at most 512 bytes); the home peer forwards the whole datagram unchanged to the registration of that connection only |

`OBSERVED_ADDRESS` status (`ObservedAddressStatus`): `2` TOKEN_REQUIRED, `3` REGISTERED, `4` UNREGISTERED, `5` FULL, `6` TOO_MANY_CONNECTIONS, `7` INVALID_NAME, `8` SIGNED_OUT (code `1` is not used).

`RESULT` status (`ResultStatus`): `1` ACCEPTED, `2` STALE (an equal or newer sequence is stored), `3` INVALID (also a bad token or a graft for a topic the peer is not in), `4` NOT_REGISTERED, `5` LIMIT_REACHED (also a host over its record rate, a full mesh, the most topics), `6` DELIVERED, `7` UNKNOWN_TARGET. Message kind code `11` is not used.

## Registration and observed address

The first `REGISTER` from an address carries no token; the peer answers `TOKEN_REQUIRED` with a 16-byte token (HMAC-SHA256 of address, port and key under a per-run secret, valid for two 60 s buckets). A proved `REGISTER` (and every refresh) whose display name and stamp nonce are no valid stamp of the sender's key at the peer's difficulty is refused with `INVALID_NAME` and registers nothing. The repeated `REGISTER` with the token registers the sender's connection at the observed address (at most 4096 registrations, granted for at most 300 s); a refresh of the connection from its registered address needs no token. Only registered connections may publish, list, subscribe and signal (`FIND_PEERS` and `SEALED` are answered to anybody within the length rule), and they receive large answers only at their registered address. Clients refresh at half the granted lifetime; a NAT remap shows as `TOKEN_REQUIRED` and the client registers again at its new address.

**Connections** (`RegistrationStore`): a peer keeps one registration per connection of a key (key, connection number), at most 8 live connections per key. A proved registration of a connection the peer does not hold is refused with `TOO_MANY_CONNECTIONS` while the key has 8 live connections there (an expired one gives its place first); the client tries again after the retry time, so the place of a crashed session frees at its registration's expiry, at most 300 s. The same connection at a new address (a NAT remap) moves its registration and leaves the other connections of the key as they are; a connection that registers at the address of another connection of its key replaces it, since one address is one socket. A `REGISTER` with lifetime `0` from a connection's registered address removes that connection only. A request that needs a registration is taken from the address of any registered connection of its sender key, and acts for that connection: a room it publishes must name that connection (`INVALID` otherwise), a subscription is the connection's own (every connection of a key has its own subscriptions), and a signal or a whisper names the target connection, which alone gets it. A `REGISTER` carries the connection start (the epoch millisecond its session began): a peer that holds a sign-out of the key (section [Community](#community-presencerecord-chatlinerecord-signoutrecord-sealedmessage)) refuses with `SIGNED_OUT` a connection other than the sign-out's kept one that started before the sign-out's timestamp, removes such a connection's registration, and drops every such registration it holds when it takes the sign-out in; the client then registers nowhere again. A client asks its nodes for more nodes with a padded `FIND_PEERS` of a random target (no card) and records what it learns in the shared peers file (section [Files](#files)): every node once after its first registration, and a listed node again while the client knows fewer than 8 learned peers, 30 s after its last answer with the interval doubling every time, at most 8 times in a session, so that a session started while its nodes knew few others learns the ones that join later.

## Peer layer (`PeerRouting`, `RoutingTable`, `PeerLookup`)

**Proof**: a peer greets seeds, candidates (senders of hello or lookup requests whose address is not proved), remembered peers and quiet known peers with padded `HELLO` requests, two per round (5 s); the answer at the greeted address proves the peer's address and key. A peer that answers a `FIND_PEERS` request at its address is proved too. A seed has no key: the first validly signed answer from its address is trusted (the answer must carry the waiting random request number); a seed with a pinned key is greeted as a known peer, so that only that key's answer counts. Every card's and every `PEERS` entry's proof is checked; an entry is used only with an IPv4 address and the same kind of address as the answering peer's (public, or local network and loopback).

**Routing table**: Kademlia k-buckets by the common prefix of the IDs, 8 peers per bucket, a replacement cache of 4 proved peers per bucket; only peers whose card says reachable (their self-test proved it) enter. Network limits: 2 peers of one IPv4 /24 (IPv6 /48) per bucket, 8 per table, and 16 of one IPv4 /16 (IPv6 /32) per table; loopback addresses are not limited. A full bucket keeps its peers (long-lived peers are preferred); a peer leaves after 2 unanswered requests in a row (lookup requests, or hellos after 10 minutes of silence) and the newest cached peer that keeps the limits takes its place. Proved leaves (and full peers without room) are known outside the table (at most 256, dropped after 60 s of silence): the self-test uses them, and the topic layer while the table is empty; they are never answered to `FIND_PEERS` nor remembered.

**Lookups**: iterative, 3 requests in flight per path, until the 8 closest peers of the path answered or failed (2 s per request with one resend, 30 s per lookup, at most 8 lookups at once). A lookup over disjoint paths (3 by default for a lookup asked by the owner, `MeshPeer.findPeers`) deals its start peers to the paths in turn, and a peer named by an answer joins only the path that asked, unless another path knows it already; a path considers at most 2 peers of one /16. A peer joins with a lookup of its own ID once its table holds a peer and its first self-test settled, again when its self-test proves it reachable (the reachable flag of its requests makes the asked peers take it into their tables), every 30 s while its table holds fewer than 8 peers, and otherwise refreshes a random bucket every 10 minutes.

**Bootstrap** (`PeerBootstrap` on `KnownNodes`, the launcher's node and the headless node): the seeds (the one seed rule: the user's node list once saved, otherwise the shipped `seeds.json`; the node's `--peer` options; a runtime run's `--seeds` and `--seed`) and the 32 best learned peers (`peers.json`: the most recent success first, then the longest known, at most 2 per /24 before the others) are greeted together; whichever answers first connects the peer. The peer records the full peers of its routing table into `peers.json` every 5 minutes and at the stop; a runtime session records the nodes that register it, its embedded peer's full peers and the nodes its listed nodes report. A learned peer is dropped after 3 starts in a row in which it was tried and did not answer, when another key answers at its address, and 30 days after its last success.

## Reachability self-test (`ReachabilityCheck`)

A peer asks up to two random known peers (helpers) for a `DIAL_BACK`, padded like a ping. A helper serves only a requester whose card has a valid proof; it forwards the request with the requester's observed address to a random third known peer and answers with that address, or answers without an address when it knows no third peer; both are shorter than the padded request. The third peer serves only a helper known at its proved address and sends a `PROBE` (shorter than the forwarded request, at most 4 at once and then 1 per second to one IP address) to the named address. The requester is reachable (a full peer) when a probe of its waiting dial-back, or any padded `HELLO` request, arrives from an address its socket never sent to (by IP address; on the loopback address by port; at most 4096 addresses remembered for 10 minutes); an accepted dial-back whose probe does not arrive within 10 s makes it not reachable (a leaf) until a later test or an unrequested hello proves otherwise. Reachable is kept; other results are tested again 5 minutes after an accepted test, after 30 s when no helper accepted or the probe came from an address the peer had sent to. A leaf-only peer is not reachable from the start and never asks.

A helper's answer and a third peer's probe both reach the address the request came from; with a spoofed source a requester makes two hosts send to a victim for one request (about 1.1 times its bytes, probes rate limited per IP address). This is kept: the probe is the test.

## Topics (`TopicKey`, `TopicSwarms`, `TopicDirectory`, `Swarm`)

A topic key is the kind (1: `1` MOD, `2` CHANNEL, `3` PLAYER) and SHA-256 of `BLNK topic 1\0`, the kind code and the name (UTF-8; a mod's topic is named by its mod id, so every version of a mod shares it; a channel's by its name with the white space cleaned and in lower case, at most 32 bytes, shared by every mod; a player's by its key in hexadecimal). The hash is a place in the routing space: the full peers closest to it are the topic's storing peers. A peer takes part in a topic while its owner or one of its registered clients uses it (a room or a record published through it, a listing, a subscription; a `LIST_ROOMS` that finds the topic new waits up to 2 s for the first joining) and leaves it 10 minutes after the last use unless it still holds an unexpired record published through it or a subscribed client; at most 256 topics.

**Joining**: the peer looks up the storing peers over 3 disjoint paths (with an empty routing table it asks the peers it knows instead), asks each with `GET_TOPIC` and announces itself with `ANNOUNCE` and the token of the answer. A storing peer keeps an announcement for 10 minutes, at most 64 members per topic (a new member replaces the older of two random ones) and 2048 topics; members look the topic up and announce again every 4 minutes, every 30 s while their mesh is empty. `GET_TOPIC` is answered by storing peers from their announcements and by members from the members they know (peer exchange), at most 16, reachable members first; the token (16 bytes, as for `REGISTER`) proves the asker's address, so nobody can announce or graft another host's address.

**Mesh**: a member grafts members until it has 6 mesh neighbours (reachable members first; a member it has no token of is asked with `GET_TOPIC` first), grafts more below 4 and prunes neighbours down to 6 above 12 (neighbours that grafted it first). At least 2 neighbours are members it grafted itself: it accepts grafts of others up to 10 (12 less that quota) and grafts while it has fewer than 2 of its own, so that members that graft a peer first cannot fill its whole mesh, and refused grafts go to other members. A neighbour not heard from for 60 s is dropped; a link without traffic for 30 s gets an empty `IHAVE`, which keeps the NAT mappings of a leaf open.

**Gossip**: a new record goes at once to every mesh neighbour and every subscribed client (`GOSSIP`); every round (5 s) the IDs of the records taken in since the last round go to the mesh neighbours and to 6 other reachable members, and the IDs of the last two rounds to the subscribed clients (`IHAVE`), who ask for the ones they have not seen (`IWANT`); a new mesh neighbour gets the IDs of every record. A record's ID is the first 16 bytes of SHA-256 of `BLNK record 1\0` and its whole wire form.

**Record checks**, in this order: records are accepted only from mesh neighbours and from a member that was asked for them; the record ID not seen before; the topic and whether the kind belongs there (rooms in mod topics, chat lines in channel topics, a presence in a player topic only from that player, a sign-out only in its player's own topic); the sequence (stale is dropped); the signature (before the rate, so that a forged record cannot spend its author's rate); the author's rate per kind (rooms: burst 8, then 1 per second; chat lines: burst 5, then 1 per second, and a line dated more than 5 s ago, a line of a backlog, from a history allowance of 32, then 1 per second, so that a peer that joins a channel gets the backlog; presences and sign-outs together: burst 16, then 1 per 5 s, so that eight connections of a player refreshing every 50 s fit); the author's stamp of the record's display name (presences and chat lines); the expiry and lifetime (the room store: 512 per topic, 8 per host key and 4 per host connection, at most 600 s ahead; the community store: 256 presences, the newest of each connection of a player wins, at most 8 connections per player (a further connection takes the place of the player's connection that expires first, if that one expires earlier), at most 300 s ahead; the 32 newest chat lines, dated at most 30 s ahead, kept 5 minutes; the newest sign-out of a player, at most 300 s ahead and dated at most 30 s ahead). Every failed check is counted and penalized (section [Receiving](#receiving)).

## Rooms (`RoomAdvertisement`, `RoomDescription`, `RoomKey`)

An advertisement (record kind 1) is a record of its mod topic, signed by its host: flags (1, bit 0 withdrawn), topic key (33), host key (32), host connection (8: the connection of the host's session that holds the room), room number (4), sequence (4), expiry (epoch ms, 8), the description, the host's home peers (count 1, at most 3, entries key 32 + address: the first nodes the host's connection is registered at), the host's settled network coordinate (flag 1: `0` none, `1` the coordinate (16) follows; a withdrawal has none), and the host's Ed25519 signature over the domain `Beacon.Link room advertisement 1\0` and every byte before it; at most 545 bytes plus the home peers and the coordinate (716 with three IPv6 entries). The description: mod fingerprint (length byte, 1 to 192 bytes: the mod identity's wire form, which names the host's mod id and version and the engine version), room name and map name (text, at most 48 bytes each, the room name not empty), players and capacity (1 each; players at most the capacity, the capacity at least 1), the room flags (1: bit 0 private, bit 1 the game started, other bits zero), the join key of a private room (32, private rooms only) and the mod data (length byte, at most 64 bytes, and the bytes).

**Mod data** (`RoomSettings.getModData`): bytes that the host's mod publishes with its room and that the mods of the searching clients read from the rooms they list; peers and clients carry them unread. A mod defines its own mod data and documents it; the demo publishes one byte, the room's turn rate (`DemoLobby`).

The room key (`RoomKey`) is host key + host connection + room number, so that two connections of one account host rooms side by side and a join reaches the connection that holds the room; a higher sequence replaces a lower one; a withdrawal stays until its expiry so gossip cannot bring the room back. Hosts refresh every 40 s with a 120 s expiry. Peers check only the topic, the signature, the expiry and the host's rate, and list the rooms of a topic; the client tells the rooms of its own mod identity (its fingerprint) from the rooms of the mod's other versions, which it lists apart with the refusal their hosts would give, and shows every room's mod id and version from its fingerprint. A room can be joined while it runs the client's mod identity, has a free place (players below the capacity) and its game has not started; the others are closed rooms, which a room list greys or hides.

**Private rooms**: a room with a password carries the public half of an X25519 join key pair its host made for the room; the password itself is never sent. A joiner proves it in its offer (section [Signals](#signals-channelsignal)): proof = HMAC-SHA256(key = the X25519 secret of the offer's ephemeral key and the join key, `SC4J Beacon.Link room password 1` || host key || room number (4) || joiner key || the password's UTF-8 bytes). The host agrees the same secret from the join key's private half and refuses an offer without the right proof (`WRONG_PASSWORD`). Relaying nodes know neither the secret nor the password, so they cannot test passwords against a proof, and a proof fits its offer only. A joiner that shares no node with the host registers at the host's home peers (they are neither learned nor remembered), so that its offer and the host's answer travel through one peer.

## Community (`PresenceRecord`, `ChatLineRecord`, `SignOutRecord`, `SealedMessage`)

**Presence** (record kind 2): flags (1, zero), topic key (33), player key (32), connection number (8), stamp nonce (8), sequence (4), expiry (8), the content: display name (text, at most 32; the name the stamp binds), mod id (text, at most 48; the launcher's is `sc4j-launcher`, `BeaconLink.LAUNCHER_MOD_ID`), mod version (text, at most 24), the first 8 bytes of SHA-256 of the mod fingerprint (equal for players who can play together), status (1: `1` available, `2` away, `3` in a room, `4` in a game), away text (text, at most 32, empty for none and unless away; others show it in their user lists and after a whisper to the player), channel name (text, at most 32, empty for none), X25519 whisper key (32, made per session), home peers (as in a room: the connection's first registered nodes), the connection's settled network coordinate (as in a room; renewed with the 50 s refresh only, so that it causes no extra records), and the player's signature over `Beacon.Link presence 1\0` and every byte before it. Every connection of a player (the launcher, a game, another computer) signs a presence of its own into its mod's topic, every channel it joined and the player's own topic, refreshes it every 50 s with a 120 s lifetime and signs it again at once when the content changes; leaving a channel or closing the session sends a presence that expires in 5 s. A connection that appears offline publishes none (an account-wide "appear offline" does not exist). Stores and clients keep the newest presence of every connection (key and connection number), so the connections of one player stand side by side.

**Merged presence** (`ClientCommunity`, what viewers show): a player is online while any of its connections has a live presence in a topic the viewer follows; of its connections, the one whose state ranks highest gives the shown state, mod and away text: in a game, in a room, online in a mod (available in any mod but the launcher), in the launcher (available with the mod id `sc4j-launcher`), away. The count of live connections is the player's device count. A user list shows each player once, merged. So a friend sees a player who starts a game from the launcher go from "in the launcher" to "in a game" and back when the game ends, never offline: the launcher's presence lives on beside the game's.

**Own player topic**: every connection subscribes to its player's own topic (it publishes its presence there too): it sees the presences of the account's other connections (the same merge, its own connection included) and the account's sign-outs.

**Chat line** (record kind 3, channel topics only): flags (1, bit 0 emote), topic key (33), author key (32), stamp nonce (8), author sequence (4), timestamp (8), display name (text, at most 32; the name the stamp binds), text (text, 1 to 255 bytes), and the author's signature over `Beacon.Link chat line 1\0` and every byte before it. It expires 5 minutes after its timestamp.

**Home peers**: a client's first registered nodes (at most 3) take part in its topics for it. `PUBLISH_RECORD` (from a registered client, of its own record) puts a record into its topic; `RECENT` subscribes the client for 90 s (the `RESULT` value; at most 256 subscribers per topic), the client renews at a third of it; with the backlog flag the peer first pushes the presences, the chat backlog and the sign-outs it holds. The peer pushes every new record of the topic to its subscribers (`GOSSIP`) and the IDs of the last two rounds every round (`IHAVE`); a subscriber asks for missed ones with `IWANT`. So the mesh of a topic runs between reachable peers only, and a client behind a NAT needs no link to other players' clients (no leaf-to-leaf links for chat). A line a home peer refuses with `NOT_REGISTERED` (it lost the client's registration, for example after a NAT remap) is held, at most 8 per topic and home peer (the oldest gives way), and published there again in sending order once the peer registered the client anew. A line travels from its author to its home peer, through the mesh when the reader has another home peer, and from there to the reader; nothing on that way waits for a round or a poll interval. A client checks every pushed record as a relay does (topic, kind, expiry, stamp, signature) and drops a record ID it has seen; it trusts its home peers for the author rates.

**Whisper** (`SEALED`): the sender seals one copy for every live connection of the target, from that connection's newest presence: it agrees a secret between a fresh X25519 key pair and the connection's whisper key, derives a one-time key (HKDF-SHA256, salt SHA-256 of `SC4J Beacon.Link whisper 1`, both player keys and both X25519 keys) and seals the timestamp (8) and text (text, at most 255) with ChaCha20-Poly1305 (zero nonce, the two player keys as associated data). It sends each signed copy, naming its target connection, to each home peer of that connection (resent every second, 4 times, until the connection's copy is delivered or every one of its home peers refused); a home peer that holds the registration of the named connection forwards the copy unchanged to it alone and answers `DELIVERED`, otherwise `UNKNOWN_TARGET`. The whisper is delivered as soon as one copy is (the other copies are still sent, so that every connection gets it), and not online when every copy was refused or ran out of attempts. Anyone may send it (the address and key rates bound it); the answer is never longer than the request. Home peers see the sender, the target and the size only; nothing is stored for an offline target.

**Sign out everywhere else** (record kind 4, `SignOutRecord`, `BeaconLinkSession.signOutOtherDevices`): flags (1, zero), the player's own topic key (33), player key (32), kept connection (8: the connection that signs it), sequence (4), timestamp (8, epoch ms), expiry (8, 240 s after the timestamp; peers take at most 300 s ahead), and the player's signature over `Beacon.Link sign out 1\0` and every byte before it; no stamp. The signing connection publishes it in the player's own topic through its home peers (`PUBLISH_RECORD`; a home peer that registers the connection later gets it too). A connection that gets a valid sign-out of its own player (pushed in its own topic) naming another connection, with a timestamp after its own connection start, ends its session with `LinkFailure.SIGNED_OUT`: it closes its channels, withdraws its rooms, sends its leaving presences, unregisters and registers nowhere again. A node that holds the sign-out drops and refuses such connections (section [Registration and observed address](#registration-and-observed-address)), the backstop for a connection that missed the push: it is refused at its next registration refresh, within half a registration (150 s), while the record lives. A connection that starts after the timestamp is not affected. Every client that takes a valid sign-out in a player topic it follows (its own or a friend's; the signing connection its own at once) drops the presences of the connections it ends from all its topics at once: every connection but the kept one whose presence sequence (a second) is at most the second of the timestamp. While the sign-out lives, it drops their later presences too, the leaving presence of an ended connection included, so that friends and the kept connection see the device count fall at once, not when the presences expire. Limit: it ends sessions; it does not revoke a stolen key (that needs a new account).

**Ignore list** (`CommunitySession.ignore`, `getIgnored`): the account's list of ignored (blocked) players, shared by every process of the account in `blocked.json` (section [Files](#files); a guest's lives in memory). An ignored player's chat lines and whispers are not handed out, and mods hide its rooms. Nothing of it goes on the network.

## Network coordinates (`NetworkCoordinate`, `CoordinateReport`, `CoordinateEstimator`)

Every host estimates its place in the latency space with Vivaldi (3 dimensions and a height; the estimated round trip time of two hosts is the distance of their points plus both heights). A coordinate is 16 bytes: the three components and the height, each a signed 32-bit count of whole milliseconds (components within 10,000 ms of the origin, the height 0 to 10,000 ms; readers refuse anything else, the smallest int included). A coordinate report adds the error (1 byte, hundredths, at most 150: the moving relative error of the host's estimates, 1.5 for a host that knows nothing). Cards (`HELLO`, `FIND_PEERS`, `DIAL_BACK`, `ANNOUNCE`, `GRAFT`), `PEERS` and `OBSERVED_ADDRESS` carry the sender's report; no message is sent for coordinates alone.

**Samples**: a peer takes the round trip time of each of its `HELLO` requests (to candidates and quiet peers) and lookup requests with the answering peer's report from the answer; a client takes the round trip time of each answered node request that was not resent, with the node's report from its last `OBSERVED_ADDRESS` or `PEERS` answer. The runtime session and its embedded peer feed one estimator (one socket, one place). A sample moves the coordinate by 0.25 times the share of the own error in both errors times the difference of the measured and the estimated time (the error follows the sample's relative error with the same weight); the height stays at least 0.1 ms; samples above 5 s are ignored; a weak pull to the origin keeps a network's coordinates from drifting. One remote host gives at most one sample every 5 minutes (the last 64 are remembered), so that a client's few nodes do not outweigh the others; a coordinate is settled after samples of 6 different hosts with an error of at most 0.6; only a settled coordinate goes into room advertisements and presences, and the estimate to a room's host or a player (`LatencyEstimate`: good up to 100 ms, fair up to 200 ms, poor above) is unknown while either side has none.

**Outliers**: a remote host may lie about its coordinate and error within the wire bounds, or delay its answers. A settled coordinate takes no sample whose measured and estimated times differ by more than a factor of 4 (a peer counts it `COORDINATE_OUTLIER` and 1 penalty point against the remote host); of a run of such outliers it takes every 8th, so that a host that moved raises its error until it is no longer settled and follows the samples again.

**Privacy**: a record's coordinate tells no more than a whole millisecond of the latency space; it carries no address. An offline-appearing player publishes no presence and so no coordinate; a room's coordinate is the host's, whom every joiner reaches anyway.

## Channels between participants (`sc4j-beaconlink`, package `channel`)

### Signals (`ChannelSignal`)

The payload of a `SIGNAL`: kind (1), the sender's connection number (8) and fields. The envelope's signed sender key with that connection is the participant the signal comes from; the `SIGNAL` names the target's key and connection, so a join names the room by the host connection it is sent to and the room number of its offer. Address candidates are a count (1, at most 8) and addresses.

| Kind | Fields after the sender's connection |
|---|---|
| `1` OFFER | initiator's receive number (8), X25519 ephemeral public key (32), join flag (1), with the flag `1`: room number (4), the joiner's mod identity (length byte and bytes) and the password proof of a private room (length byte `0` or `32`, and the bytes; section [Rooms](#rooms-roomadvertisement-roomdescription-roomkey)); then the candidates |
| `2` ANSWER | initiator's receive number (8), responder's receive number (8), ephemeral public key (32), candidates |
| `3` REFUSAL | initiator's receive number (8), reason (1): `0` the host does not hold the room, otherwise the code of the engine `JoinRefusal` (engine version, mod identity, full room, `9` wrong password) |

The signal's envelope is signed by the sender and names the target, so both ephemeral keys and receive numbers are authenticated by both identities. Of two participants the one with the lower key offers, of two connections of one account the one with the lower connection number (both compared unsigned); a joiner always offers. A host keeps at most 16 joins that did not connect yet; a newer one takes the place of the oldest.

### Key schedule (`ChannelKeys`)

transcript = SHA-256(`SC4J Beacon.Link channel 1` || initiator identity || initiator connection || responder identity || responder connection || initiator ephemeral || responder ephemeral || initiator receive number || responder receive number), so that a channel's keys belong to its two connections and no other connection of either account; PRK = HMAC-SHA256(key = transcript, X25519 secret); key(initiator -> responder) = HMAC-SHA256(PRK, `initiator to responder` || 0x01), key(responder -> initiator) = HMAC-SHA256(PRK, `responder to initiator` || 0x01). An all-zero secret is refused; secrets are zeroed after use.

### Datagrams (`ChannelDatagramUtils`, `ChannelCipher`, `ChannelFrame`)

`BLCH` (4) | receiver's receive number (8) | counter (8) | ChaCha20-Poly1305 ciphertext of the frame | tag (16). The associated data is the 20 header bytes, the nonce 4 zero bytes and the counter. Counters start at 0 per direction; a 256-counter replay window is checked before decryption and recorded after authentication. At most 1200 bytes. Channel datagrams share the client's UDP socket with envelopes and are told apart by the magic.

**Frame types** (`ChannelFrameType`): `1` PROBE, `2` PROBE_ACK (hole punching), `3` DATA (at most 1024 bytes), `4` PING, `5` PONG (keepalive every 2.5 s, delay), `6` CLOSE, `7` RELAY_QUERY, `8` RELAY_STATUS, `9` RELAY_FORWARD, `10` RELAY_DELIVER; a relay frame names the other participant in its wire form (40 bytes). A pair without a direct path uses another participant with direct channels to both, chosen by the lowest measured delay: A sends RELAY_FORWARD(B, sealed A->B datagram) to C, C sends RELAY_DELIVER(A, same bytes) to B. The relay cannot read or change it and passes at most a budget per pair. Peers never relay channel datagrams of games they do not take part in.

### Overlay (`LinkOverlay`, `ChannelOverlay`)

An overlay datagram is a port byte and at most 1023 bytes, addressed by participant. Ports 1 to 15 are the engine's: `1` engine lobby (network lobby 3: its participant lists name each member's participant in its wire form), `2` engine lockstep transport (every engine-lobby mod). Ports 16 to 255 (`LinkOverlay.FIRST_MOD_PORT` on) are free for a mod's own protocols; each mod documents its ports.

## Files

- `<install>/launcher/seeds.json` (shipped with the launcher, replaced per release) and `<install>/userdata/beaconlink/nodes.json` (the user's node list; the launcher writes it when the user saves it and passes it to the runtime as `--seeds`; until it exists, the launcher's editor and node use `seeds.json` in its place and pass that; `NodeListFile`): `{"format": 1, "nodes": [...]}` with entries `"host:port"` (any key) or `{"address": "host:port", "key": "<64 hex digits>"}` (pinned key, an advanced option). At most 64 KiB, nesting at most 8; IPv6 hosts in brackets.
- `<install>/userdata/beaconlink/node.json` (the launcher node's settings): `{"format": 1, "role": "automatic", "port": 7455}`; role `automatic` (listens on the port, a full peer once its self-test passes) or `off` (leaf-only on a free port); missing: automatic on 7455.
- Shared files (`SharedFile`): several processes of one computer (the launcher's node, every game, a headless node in its own folder) use one file at once. A writer opens the file itself read-write, takes an exclusive lock of the whole file, reads it, merges its own changes into it, writes the result in place from the start, truncates the rest, forces it to the disk and releases the lock; a reader takes a shared lock. No rename, no temporary or backup file. A missing or empty file holds nothing; a damaged file (a writer that ended during a write) holds nothing with one warning and is written again by the next merge. Each process takes the merged result as its view, so it sees the other processes' additions.
- `<install>/userdata/beaconlink/peers.json` and a node's `<state>/peers.json` (`PeerStore`, a shared file): `{"format": 1, "peers": [{"key": "<hex>", "address": "<IP literal>", "port": <port>, "firstSeen": <ms>, "lastSuccess": <ms>, "failures": <n>}, ...]}`, at most 256 peers, at most 256 KiB; `lastSuccess` 0 is a peer another node reported that never answered. Merge: union by key; of two entries of one key the newer `lastSuccess` gives address, port and failures, on an equal `lastSuccess` the larger `failures`; `firstSeen` is the minimum; of two keys at one address the newer `lastSuccess` stays; an entry with 3 failures, or older than 30 days (its `lastSuccess`, or `firstSeen` if it never answered), is dropped; the list is cut at 256 in the order `lastSuccess` descending, `firstSeen` ascending, key ascending. A process merges only the entries it changed since its last merge, so an entry another process dropped stays dropped. Merged every 5 minutes and at the stop; leaves are never written.
- `<install>/userdata/beaconlink/peer.key`, a node's `<state>/identity.key`: key files as above. The proof nonce is not stored: a peer finds it again at each start.
- `<install>/userdata/beaconlink/node.lock`: an empty file that the launcher running the node holds locked.
- `<install>/userdata/beaconlink/accounts/<id>/` (an account, section [Identities](#identities)): `identity.key` (the player key), `account.json` (`{"format": 1, "name": "<name>", "difficulty": 24, "stamp": <nonce>, "lastUsed": <epoch ms>}`: the name and the player stamp that binds it to the key; a folder whose stamp does not bind its name holds no account), `friends.json` (`PlayerListStore`, a shared file: `{"format": 1, "players": [{"key": "<hex>", "time": <ms>, "removed": false}, ...]}`; per key the newest `time` wins, a removal on an equal time; a removal stays as a removed entry for 30 days, so that a process that still holds the friend cannot bring it back; at most 16 listed players, the oldest additions give way; merged at once on each own change and read again every 10 s), `blocked.json` (the ignored players, the same format and rules as `friends.json`, at most 256 listed players) and `account.lock` (an empty file every process that uses the account holds with a shared lock).
- Topics, announcements, meshes, records, registrations, subscriptions, whisper keys, penalties and the graylist are kept in memory only.

## Versioning

Protocol 1 is the only protocol. The envelope's version byte is `1`; receivers drop other versions, and unknown kinds and capability bits are dropped or ignored. Before 1.0 the protocol number, the record and file versions and the numbers in the hash and signature domains are all `1`, and a field layout or meaning may change in place. Peers send their software version in `HELLO` and `PONG` (`MeshPeer.SOFTWARE`, now `sc4j-beaconlink-peer 0.11`); no rule depends on it.

The peer layer routes IPv4 only: the session socket of the runtime (`UdpDatagramEndpoint`) is IPv4, and one socket per process is required (the address a peer observes must be the address hole punching uses). `PEERS` entries with IPv6 addresses are dropped and IPv6 seeds cannot be reached; the address encoding and the /48 and /32 network limits already cover IPv6.
